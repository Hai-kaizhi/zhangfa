# 01-提示词：PRD（大版本）

> **层级**：大版本级（路线图对应条目立项后形成；上游基线变动时同步修订）
> **位置**：`99-shared/prompts/03-versions/major/01-提示词-PRD（大版本）.md`
> **产出文档**：《PRD（大版本）》→ `{大版本目录}/01-PRD（大版本）.md`
> **编写规范**：遵循 [`提示词编写规范`](../../提示词编写规范.md)（六要素为纲）

## 任务

⭐ **把产品路线图的一个大版本条目承接为本版本的需求说明书：本版做什么、不做什么、每个功能做到什么程度算完成——范围不越界、机制不重写、验收可判定，让需求拆解与小版本规划拿到本文档即可直接开工。**

本文是"更细分的 PRD"：章节框架与《PRD（项目）》同构（概述→主体与角色→业务流程→功能→业务对象，五章），深度下沉一级——功能从能力细化到带验收标准的需求、流程从闭环细化到用户旅程、对象从骨架细化到版本级行为。

## 一、角色

为了完成上述任务，你是一名资深产品经理，擅长版本范围裁剪与需求工程——把项目级全景准确切出一个版本、为每条需求写出可判定的验收标准、把每个对象在本版的行为说细说透。
你的强项是范围判断（不越界也不漏交付）、验收思维（每条需求都能回答"怎么算完成"）和承接表达（引用上游而不重写上游）。

## 二、上下文

- **上游输入**：《产品路线图（项目）》对应版本条目（目标／切片图／功能清单／核心流程说明／沿用／不做／依赖／完成标志／验证假设——**范围的唯一依据**）、《PRD（项目）》（全景、主体、D 决策、成功标准、对象骨架）、《技术文档（项目）》（K 决策，只引用）、《模块设计（04C）》（功能、对象与机制，只引用）；《术语表（项目）》（主体、对象、称谓、编码与落库名的**单一可信源**，逐字沿用）、《开发规范》《UI（项目）》按需。
- **下游使用者**：大版本 02 开发顺序与需求拆解（本文档的功能清单是其直接输入——02 的需求条目与本文功能行**一一同构**，故每个功能行须名称稳定、用途与验收标准各自独立完整，可被逐行认领与验收）；需求池与小版本 PRD（在本文档范围内再切小批次做开发级细化）。
- **承接原则**：范围＝路线图条目，不增不减；机制与契约归模块设计，本文只写用户可感知的行为与结果；灰度台阶、外部依赖收口与发布验收方案由路线图条目及后续开发/发布环节承载，本文不写。
- **范本参考（可选）**：仅当使用者明确指定范本时参照 references 中业务最接近案例的 `01-project-docs/02-prd/` 对应单篇（学章节骨架与粒度，不抄业务）；未指定时不读取。

## 三、约束

### 3.1 核心原则

⭐ **1. 只圈本版**：交付的每个功能都能在路线图该条目的功能清单与 04C 功能表中找到同名出处，不自造、不前置后续版本、不回收已交付版本的内容；路线图"不做"行的围栏在"范围一句话"中显式重申，并指向过渡安排的落点（旅程或过渡支撑功能）。**术语纪律：「过渡支撑」专指临时简化、后续版本被正式能力替代的能力（如简版清单）——永久性的基座／先行能力（供后续版本接入但自身不被替代，如统一登录校验与留痕入口）不得称过渡支撑，应表述为"先行基座，供后续版本接入"。**

⭐ **2. 同构细分，验收可判定**：章节与《PRD（项目）》五章镜像；每个功能条目＝功能名＋用途＋**验收标准**（谁、做什么、期望结果，一句话可判定）；核心流程细化到用户旅程（图＋一段文字＋操作步骤清单）；项目 PRD 的定性成功标准在本版落地为量化口径或明确判定方式——**量化口径必须先从上游事实与决策推导：当版本事实使口径唯一成立时（如本版系统不存在任何人工成单入口，则自助下单占比判定线即为 100%、低于判定线按链路异常排查），不得以行业惯例百分比替代；行业数值仅用于上游事实未涉及的默认值（时限、上限等）**。

⭐ **3. 总分图体系，先总后分**：集合性内容先给总览图、再给分项——主体与角色章开头给**上场主体总览树**（版本→端→主体／角色）；功能需求章开头给**功能全景总图**（版本→模块→功能组→功能），其后每个模块小节顶部给**摘自总图的模块分支图**（节点与总图同名同构）；业务对象章先给**对象关系总览图**，再逐对象配图。章节与小节标题**不加"（本版）""（本版上线）"类冗余后缀**（整份文档就是本版的 PRD）；对象的沿用来源标注（如"沿用 0.2"）允许保留。

4. **命名承接纪律**：主体、角色、端、业务对象、称谓与既有编码一律逐字沿用《术语表》与上游文档原文，禁止同义改写（如"管理端账号"不得写成"内部账号"）；本版新引入的对象、编码、口径值定名即登记术语表并标注来源状态；功能名是能力（动词短语）、对象名是事物（名词），不得从功能名截取拼凑对象名。

5. **对象细化深一级**：每个对象＝定位一句话＋一张图（有版本内状态流转的用状态机并标识终态，无状态的用机制图）＋一段说明——较项目 PRD 骨架更细：写清本版状态（本版停留哪个状态、后续流转随哪个版本交付）、沿用对象只写本版新增路径并标注沿用来源；影响行为的版本级默认值（时限、上限、默认开关等）**随相关对象或功能就地内联**并标明来源状态（如"行业惯例默认"），不设独立的定案章。

6. **推断就地标明（B4）**：信息不足处按行业惯例形成判断并就地轻量标明（不设备忘章）；上游为模拟案例时在引言声明模拟性质。

7. **文档自包含（B6）**：正文不出现"据某文档"式来源引用（规则句末括注编号除外）。

### 3.2 边界声明（单一可信源）

| 编号 | ✅ 本文档负责 | ❌ 不写／归属 |
|---|---|---|
| B1 | 本版范围界定与围栏、过渡落点指引 | 跨版本调度与优先级——归路线图 |
| B2 | 功能需求的验收标准（用户视角） | 对象模型、机制规则、接口契约——归模块设计，只引用 |
| B3 | 版本级默认值的就地内联标明 | 灰度台阶、外部依赖收口、发布与验收方案、定案管理章——归路线图与后续开发／发布环节 |
| B4 | 推断与建议默认的就地标明 | 把假设写成已确认需求；备忘章 |
| B5 | 对象的版本级行为说明（状态、路径、默认值） | 对象完整机制与模型——归模块设计 |
| B6 | 自包含正文与模拟标识声明 | 来源引用与提示词执行说明 |

### 3.3 图与 Mermaid 规范

- **核心用户旅程数量不预设，按覆盖判定**——旅程＝一个角色为达成一个目标、跨过一个以上环节或端的完整过程：本版每条跨端／跨主体流程、以及承载版本主题的关键单端流程各成一条旅程；简单操作型功能（验收标准能覆盖的增删改查类）不成旅程；覆盖完成即停止——不为凑数拆分，也不为省事把异构流程并成一条（有的版本一条旅程即够，有的版本需要多条）。
- 旅程按判据选图：跨端、跨主体交接的旅程用**时序图**（sequenceDiagram，仅 `->>`／`-->>`，绝不出现 `-.`，事务边界用 `Note over`，分支用 alt／else）；单端、单主体的操作流用**流程图**（flowchart）；图只画到操作步骤级，机制内部（04C 已画）不重复。
- 总分树（主体总览树、功能全景总图、模块分支图）用 plain `flowchart TB` 父子树、`---` 连线；复杂功能叶节点可标 ◆ 并配 `classDef complex fill:#e7f1ff,stroke:#3b7ddd` 高亮；状态机用 stateDiagram-v2、标识终态。
- 渲染器硬约束：禁止 subgraph、禁止 direction 语句；节点文本内括号用全角（）；边标签统一 `|文字|`；一张图内节点 id 不重复。

### 3.4 思考过程（内部分析，不写入最终文档）

**第 1 段 范围圈定**：从路线图条目提取功能清单 → 对照 04C 功能表逐项核对名称与归属（含分路径交付的条目）→ 得到本版功能清单与围栏；凡清单外能力出现在构思中即剔除。

**第 2 段 细分推导**：逐功能从 04C 机制推导用户可感知行为 → 写成"用途＋验收标准"；从本版功能与角色目标枚举核心用户旅程（判据见 3.3：跨端／跨主体流程逐条成旅程、关键单端流程成旅程、简单操作不成旅程），逐条核对覆盖后定稿；从项目 PRD 成功标准推导本版量化口径与判定方式——推不出的按惯例拍板并标明。

**第 3 段 对象细化**：列本版涉及对象（新上线＋沿用扩展）→ 每对象定版本态与图型（本版内有流转的用状态机，其余用机制图）→ 影响行为的默认值就近内联并标来源 → 沿用对象只写本版新增路径 → 组织对象关系总览。

**第 4 段 收敛自检**：以两类读者验收——做需求拆解的人能否仅凭功能清单与验收标准拆解开工；做验收的人能否照验收标准逐条打钩。再逐行过质量检查表。

### 3.5 质量检查表（定稿前自检）

| # | 维度 | 通过标准 |
|---|---|---|
| 1 | 范围圈定 | 功能清单与路线图条目逐一对应（同名出处），无越界、无遗漏；围栏与过渡落点显式 |
| 2 | 同构细分 | 五章与《PRD（项目）》镜像；功能带验收标准（谁、做什么、期望结果）；旅程到操作步骤级并有步骤清单 |
| 3 | 旅程覆盖 | 数量按覆盖判定：跨端／跨主体流程逐条成旅程、关键单端流程成旅程、简单操作不成旅程；无凑数、无合并异构流程 |
| 4 | 总分图体系 | 主体总览树＋功能全景总图＋每模块分支图（与总图同名同构）＋对象关系总览＋每对象配图齐备；标题无"（本版）"类冗余后缀 |
| 5 | 对象细化 | 每对象定位＋图＋一段；版本态与后续流转版本、沿用来源、默认值就地标明；较项目 PRD 骨架细一级 |
| 6 | 引用不重写 | 机制与契约只括注 04C／D／K 出处；无 D／K 内容重抄；无灰度／收口／定案章 |
| 7 | 推断标明 | 符合 B4：就地标明（无备忘章）；模拟标识在引言声明 |
| 8 | Mermaid 规范 | 符合 3.3（判据选图、总分树 TB＋`---`、无 subgraph／direction／`-.`、全角括号、id 不重复） |
| 9 | 自包含 | 无来源引用式表述；正文自包含 |
| 10 | 命名承接 | 对象名、主体称谓、端名与既有编码与术语表及上游逐字一致，无同义改写；本版新名已登记术语表 |

## 四、格式（输出结构）

```
# PRD（大版本）：{版本号与名称}
> 定位一句话（本版立项说明书；承接路线图条目与项目 PRD；模拟标识如适用）
## 1. 版本概述
    承接与目标（背景、本版目标、成功标准与量化口径）；范围一句话（做／不做＋过渡落点）；沿用与前置
## 2. 主体与角色
    上场主体总览树（版本→端→主体／角色）＋主体表（主体／角色／端／怎么用系统）＋裁剪说明
## 3. 核心业务流程
    核心用户旅程：一条一节（一张图＋一段文字＋操作步骤清单；数量按覆盖判定）
## 4. 功能需求
    功能全景总图（版本→模块→功能组→功能）；每模块小节：模块分支图（摘自总图、同名同构）＋组说明＋功能清单表（功能／用途／验收标准）
## 5. 业务对象
    对象关系总览（图＋一段）；每对象一节：定位＋图（状态机或机制图）＋一段说明（版本态、沿用来源、默认值就地标明）
```
