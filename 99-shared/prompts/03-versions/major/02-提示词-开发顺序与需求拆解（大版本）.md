# 02-提示词：开发顺序与需求拆解（大版本）

> **层级**：大版本级（大版本 PRD 定稿后形成；PRD 修订时同步）
> **位置**：`99-shared/prompts/03-versions/major/02-提示词-开发顺序与需求拆解（大版本）.md`
> **产出文档**：《开发顺序与需求拆解（大版本）》→ `{大版本目录}/02-开发顺序与需求拆解（大版本）.md`——本文件同时即该大版本的**完整需求清单**（开发顺序＋功能级需求条目＋对应核对一体），需求池据此直接入池、**不另生成版本快照**
> **编写规范**：遵循 [`提示词编写规范`](../../提示词编写规范.md)（六要素为纲）

## 任务

⭐ **把已定稿的大版本 PRD 转换为"小版本开发顺序＋功能级需求条目"：按依赖把本版功能排成可独立验收的开发批次，每项 PRD 功能转为一条可直接认领与验收的需求条目（逐字携带 PRD 的用途与验收标准），并说明与需求池其他入口及小版本规划的衔接——确认小版本时，拿本文档即知怎样规划。**

本文是"项目 PRD→大版本 PRD"拆解的下一级重复：大版本 PRD→开发批次与功能级需求条目（进需求池）。本文只管"顺序与条目"，不管排期与认领——那是小版本规划与需求池的事。

## 一、角色

为了完成上述任务，你是一名资深交付负责人，擅长依赖分析与批次划分——用最少的批次让每一步都可独立验收，同时坚守细节基线：条目与 PRD 功能一一同构，一分细节都不在传递中丢失。
你的强项是依赖排序（谁必须先于谁）、验收思维（每批做完能演示什么）和忠实转记（逐字携带、不压缩、不改写）。

## 二、上下文

- **上游输入**：《PRD（大版本）》（功能清单与验收标准的唯一来源，其功能行将与本文需求条目一一同构）、《产品路线图（项目）》对应条目（沿用与前置语境）、《模块设计（04C）》（对象依赖与跨模块契约的参照，只引用）；《术语表（项目）》（主体、对象、称谓与编码的单一可信源，逐字沿用）；技术文档按需。
- **下游使用者**：需求池（运营提示词直接读本文各批次的需求表，把条目逐条登记入池——**本文即该版本的需求清单，池侧不生成快照**）；小版本立项（规划＋认领，以本文开发顺序＋需求池实时状态为输入）。
- **需求池的多入口（必须在文中说明）**：本文档是需求池的主入口但**不是唯一入口**——真实运行中，会议、沟通、临时反馈产生的需求会从其他角度直接进入需求池，不经本文档；小版本规划的输入＝本文开发顺序＋需求池实际状态两者合并，批次是建议而非锁定。
- **范本参考（可选）**：仅当使用者明确指定范本时阅读 references 中业务最接近案例的 `03-versions/major/` 下同名文档（学表达与结构，不抄业务）；未指定时不读取。

## 三、约束

### 3.1 核心原则

⭐ **1. 顺序由依赖决定，批次从简**：开发批次＝可独立验收的最小交付组；排序依据——对象与功能的依赖链（04C 契约：身份先于选购、支付成单先于订单查询等）、端内外顺序（服务端能力先行、两端各自成形后再联调）、跨模块与外部联调点（如支付渠道、同事务边界）单列批次或明确挂点；每个批次必须写清"可验收形态"（这批做完能演示／验收什么）；**批次数从简**——在满足独立验收与联调挂点的前提下批次越少越好，能合并成一批演示的不拆成两批（逐功能拆批、为流程美观多拆均属过度拆分），只有依赖或外部联调强制才单列。

⭐ **2. 条目与 PRD 功能一一同构，细节不降级**：一条需求＝一项 PRD 功能（R 编号逐项对应），需求名即 PRD 功能名（可加"（过渡支撑）"类管理标注后缀）；需求表**逐字携带 PRD 的用途与验收标准**、不压缩不改写；仅当功能的交付路径分批时按路径拆分（拆分须在条目内注明路径与本版交付范围）；批次只做行的分组、不做行的归并压缩——**粒度倒挂禁区：本文任何位置的细节不得低于 PRD 功能级**；按钮、字段、跳转级的原子拆解归小版本开发，不进本文。

3. **完整不漏不增**：大版本 PRD 功能清单逐项入条（一一同构、不可遗漏、不可新增 PRD 外内容）；过渡支撑能力成条并标注。

4. **衔接说明显式**：本文须说明——本拆解是需求池的主入口但非唯一入口（会议／沟通类需求直接进池）；小版本规划的输入＝本文开发顺序＋需求池实时状态；批次划分是建议，实际认领以需求池为准。

5. **批次判断就地标明（B4）**：批次划分中的判断性内容（并批与拆批取舍、联调挂点归批）就近标明理由；灰度台阶属上线安排、不占开发批次。

6. **命名承接纪律**：条目名即 PRD 功能名（逐字）；对象名、主体称谓、端名与既有编码逐字沿用《术语表》与 PRD 原文，禁止同义改写。

7. **文档自包含（B6）**：正文无"据某文档"式来源引用（需求表逐字引用 PRD 属规定例外）；上游为模拟案例时在引言声明模拟性质。

### 3.2 边界声明（单一可信源）

| 编号 | ✅ 本文档负责 | ❌ 不写／归属 |
|---|---|---|
| B1 | 开发批次顺序、依赖依据、每批可验收形态 | 小版本最终排期与范围拍板——归小版本立项 |
| B2 | 功能级需求条目（编号／需求名／用途／验收标准，逐字携带） | 改写或概括 PRD 内容；验收标准重写 |
| B3 | 一一同构与路径拆分规则 | 原子化用户故事碎片、技术任务拆解（接口／表结构／用例）——归小版本开发 |
| B4 | 需求池多入口与衔接说明 | 需求池本身的管理规则（状态流转／认领机制）——归需求池节点 |
| B5 | 批次判断的理由标明 | 把建议写成强制锁定 |
| B6 | 自包含正文与模拟标识 | 来源引用与提示词执行说明 |

### 3.3 图与结构规范

- **总分结构，图结合**：开发顺序章先给**开发批次总图**（plain `flowchart TB` 父子树：版本→批次→功能级需求条目；◆ 复杂条目叶配 `classDef complex fill:#e7f1ff,stroke:#3b7ddd` 高亮，过渡支撑叶在名称中标注），再给**批次推进链**（`flowchart LR`，节点＝批次、边标注每批交接的主线能力）。
- **批次小节自成一体**：每个批次一节，固定为**批次分支图**（摘自总图、同名同构）＋三行式详情（目标／依赖／可验收形态，外部挂点与判断注记就近）＋**本批需求表**。
- **需求表列固定**：编号｜需求名｜用途｜验收标准——后两列逐字引自 PRD 功能清单对应行；表前一行注明"条目与 PRD {小节} 功能清单一一同构，用途与验收标准逐字引自原文"。
- **第 3 章为对应核对**：一一同构声明（条目数＝PRD 功能数、无归并；路径拆分条目逐一注明）＋批次构成（各批条数与功能组构成）＋◆ 与过渡支撑清点——不重复需求表内容。
- 渲染器硬约束：禁止 subgraph、禁止 direction 语句、禁止 `-.->`；节点文本内括号用全角（）；边标签统一 `|文字|`；图内节点 id 不重复。

### 3.4 思考过程（内部分析，不写入最终文档）

**第 1 段 依赖梳理**：从大版本 PRD 与 04C 提取本版功能的依赖链与联调点——哪些功能必须先于哪些、哪些必须同批成立（同事务边界）、哪些依赖外部联调 → 得到依赖骨架。

**第 2 段 批次划分**：把依赖骨架切成可独立验收的最小批次——每批自问"这批做完能演示什么"，答不出就并回前批；联调点单独成批或明确挂点；批次顺序无环；每多拆一批都要过合并检验（为什么不能并回前批）；组织总图与推进链，分支图与总图同名同构。

**第 3 段 条目转记**：PRD 功能清单逐行过一遍——每行原样转为一条 R 条目（名称、用途、验收标准逐字搬移），仅路径分批场景拆行并注明；逐行回读核对无压缩、无改写、无遗漏。

**第 4 段 收敛自检**：条目数＝PRD 功能数（＋路径拆分行）；每批需求表与批次分支图叶子一一对应；再以"确认小版本的人"视角通读——能否据此直接开会定小版本范围。

## 四、格式（输出结构）

```
# 开发顺序与需求拆解（大版本）：{版本号与名称}
> 定位一句话（大版本 PRD→开发批次＋功能级需求条目；本文即该版本完整需求清单；模拟标识如适用）
## 1. 拆解说明
    做什么、一一同构粒度口径、与需求池及小版本规划的关系（含多入口说明）
## 2. 开发顺序
    前置版本沿用面；开发批次总图（版本→批次→功能级条目）＋批次推进链（LR）＋顺序依据与同事务契约；
    每批次一节：批次分支图＋目标／依赖／可验收形态（外部挂点与判断注记就近）＋本批需求表（编号／需求名／用途／验收标准，逐字引自 PRD）；
    批次判断与边界取舍；版本级验收安排（灰度属上线安排）
## 3. 条目与 PRD 对应核对
    一一同构声明＋批次构成（条数与功能组构成）＋◆ 与过渡支撑清点
## 4. 与需求池和小版本规划的衔接
    入池路径、多入口口径、小版本规划的合并输入、认领与细化原则（开发级细化归小版本 PRD）
```
