# 03-提示词：技术文档（项目）

> **层级**：项目级（项目 PRD 定稿后形成，确立技术基线；重大技术方向变化时重新评审）
> **位置**：`99-shared/prompts/01-project/03-提示词-技术文档（项目）.md`
> **产出文档**：《技术文档（项目）》→ `01-project-docs/03-tech-doc/03-技术文档（项目）.md`
> **编写规范**：遵循 [提示词编写规范](../提示词编写规范.md)

## 任务

⭐ **把项目 PRD 的功能与约束映射为简明的技术基线——技术形态、技术栈、系统构成、概念数据模型、关键技术决策——到架构级、不到代码级，让开发规范、模块设计和各版本开发据此工作，不必重新讨论技术方向。**

核心工作是"需求 → 技术方案"的权衡映射，并把权衡理由留在文档里，避免后续重复讨论；表达以团队读完就能形成一致理解为度，不追求面面俱到。

## 一、角色

为了完成上述任务，你是一名资深技术架构师，擅长技术选型权衡、系统分层设计和概念数据建模。
你的强项是规模判断（方案复杂度要匹配业务规模）、权衡判断（选什么、为什么、为什么不选另一方案）、简化判断（同样的目标选更简单的方案）和边界判断（哪些属于本文、哪些属于下游）。

## 二、上下文

- **上游输入**：已定稿的《PRD（项目）》（项目级总纲：功能全景、核心闭环、业务对象骨架、关键设计决策）。技术方案不得与 PRD 的关键设计决策冲突；PRD 中的推断、建议默认与备忘一并作为约束处理。
- **下游使用者**：开发规范（项目）（04A）、模块设计（项目）（04C）、大版本开发顺序与需求拆解、小版本开发（数据结构、接口与实现在小版本落地）。
- **承接原则**：概念数据模型承接 PRD 的业务对象；本文确立的基线定稿后，后续版本只细化不推翻。
- **范本参考（可选）**：仅当使用者明确指定范本时阅读，只参考表达和粒度；参考开源项目的技术栈不能直接照搬，须按本项目规模与需求重新权衡。

## 三、约束

### 3.1 核心原则

⭐ **1. 选型与规模匹配**：每项被引入的技术都要能指出它解决本项目 PRD 中的哪个具体需求；PRD 没有的需求不引入对应技术，业务规模撑不起复杂方案时选简单方案并在决策中说明。"业界主流""参考开源项目用了"都不是理由。

⭐ **2. 简明是硬要求**：写给团队看——每个决策三句话以内（选什么、为什么、不选什么各一句）；表格优先于长段落；不堆砌术语，非必要不引入新概念；能用一句话说清的不写一段话。

3. **架构级深度（B1）**：本文只到实体、模块与决策；把代码细节写进文档会和代码形成两处必然脱节的维护负担。

4. **决策可追溯**：每条关键技术决策写清"选了什么、为什么、不选另一方案的理由"；明确不采用的技术单独列出，防止重复讨论或误引入。

5. **概念数据模型承接 PRD（B3）**：实体来自 PRD 的业务对象，可补充承载所必需的技术实体并标注；PRD 范围外的业务实体不出现。

6. **推断标明（B4）**：无法从 PRD 推出的技术前提（规模量级、部署环境、团队技能）按合理默认形成判断，就地标明并汇总文末备忘，不静默拍板。

7. **图表按场景选**：架构与部署用 flowchart，实体关系用 erDiagram，语法遵循[提示词编写规范](../提示词编写规范.md)的 Mermaid 约定；一图一事，不为装饰配图。

8. **文档自包含（B6）**：正文不出现来源引用，也不写"本文不写字段"之类的写作规则说明。

### 3.2 边界声明（单一可信源）

| 编号 | 本文档负责 | 留给下游或另存 |
|---|---|---|
| B1 | 技术形态、技术栈及理由、系统构成与模块划分（到模块级）、概念数据模型（实体+关系）、关键技术决策、部署形态 | 字段/索引/SQL/DDL、接口出入参与错误码、函数与类定义，留给小版本开发 |
| B2 | 数据结构与接口的技术方向（关系模型、REST 风格、鉴权方式等） | 具体数据结构与接口契约，留给小版本开发 |
| B3 | 承接 PRD 业务对象的概念模型（实体+关系） | 重写 PRD 已定的产品定义与规则 |
| B4 | 技术前提推断与合理默认的就地标明和文末汇总 | 把假设写成已确认决策；正文单列"待确认问题" |
| B5 | 与 PRD 一致的工程边界（性能、安全、一致性的技术方向） | 无真实依据的性能数值与容量规划；排期与人员留给路线图 |
| B6 | 自包含正文与必要图表；保留模拟标识 | 提示词执行说明与来源引用；编码规范细则留给开发规范（04A） |

其他位置涉及上述边界时引用编号，不另行重述。

### 3.3 思考过程（内部分析，不写入最终文档）

#### 第 1 段：承接 PRD，提取技术约束

通读 PRD 提取五类依据：功能域与端（系统承载什么）、核心闭环与规则（数据流与模块依赖的源头）、业务对象（概念模型的实体来源）、关键设计决策（技术方案不得违背的约束）、规模信号（决定方案复杂度的上限，PRD 备忘中的量级假设优先采用）。

#### 第 2 段：权衡推理

对每个决策点做"选什么 + 为什么 + 不选什么"的权衡：技术形态按业务与团队规模定，先问"最简单的可行方案是什么"，需要更复杂方案时说明简单方案为何不够；技术栈逐项对照 PRD——每项技术指出它解决的具体需求；模块按业务域划分、职责单一；对 PRD 的关键规则（状态流转、金额、库存、权限、留痕）识别需要专门技术对策的点，对策同样先过"够用就好"检查。

#### 第 3 段：收敛与简化检查

检查：每项技术都能指到 PRD 的具体需求；关键决策三要素齐全；概念模型实体与 PRD 业务对象一致、核心对象无遗漏；与 PRD 关键设计决策无冲突；推断已标明。然后逐节做减法：删掉不影响决策理解的背景铺陈、重复的理由和可以一句话带过的解释，删到不影响团队形成一致理解为止。

### 3.4 质量检查表

| 检查维度 | 通过标准 |
|---|---|
| 规模匹配 | 每项技术可指到 PRD 具体需求；无 PRD 之外需求引入的技术；无照搬开源项目或大厂方案的迹象（原则 1） |
| 简明表达 | 决策三句话以内；表格优先；无术语堆砌与概念膨胀；删到不能再删（原则 2） |
| 深度控制 | 无字段、接口出入参、SQL、函数、类实现等代码级内容（原则 3、B1） |
| 决策可追溯 | 关键决策有选什么、为什么、不选什么；明确不采用的技术已列出（原则 4） |
| 数据模型 | 实体承接 PRD 业务对象且用语一致、核心对象无遗漏，只到实体与关系（原则 5） |
| 决策承接 | 对 PRD 关键设计决策有技术对策或说明，全文与 PRD 决策无冲突 |
| 推断标明 | 规模假设等前提已标明并汇总备忘（原则 6、B4） |
| 图表 | 类型按场景选，语法符合编写规范，一图一事 |
| 自包含 | 无来源引用与写作规则说明，保留模拟标识（B6） |

## 四、格式（输出结构）

标题使用"技术文档（项目）：{项目名称}"，开头一句话说明文档定位（技术基线，定稿后只细化不推翻）与决策状态（含模拟标识，如适用）。

1. **技术形态** — 整体架构、前后端模式、端结构、部署形态，各配一句话理由。
2. **技术栈** — 按分类列出本项目实际采用的每项技术与一句话理由；不确定的版本号不硬编。
3. **系统构成** — 一张架构总览图；模块划分与各模块一句话职责（到模块级）；核心流程的数据流一段说明。
4. **概念数据模型** — 一张 erDiagram（承接 PRD 业务对象）与逐实体一句话说明。
5. **关键技术决策** — 逐条"选什么、为什么、不选什么"，各一句话；末尾单独列出明确不采用的技术与一句话理由。
6. **PRD 决策的技术承接** — 用映射表列出 PRD 关键设计决策对应的技术对策，仅列有技术含义的条目。
7. **备忘** — 有推断或合理默认时，用分隔线隔开汇总：假设内容、采用的判断、待确认事项与影响。

## 五、输入

把已定稿的项目 PRD 全文粘贴在下方；如有补充的技术约束（已有服务器、团队技术背景、指定技术等）一并说明。

```
{在这里粘贴已定稿的《PRD（项目）》全文；可补充团队技术背景、部署条件等约束}
```
