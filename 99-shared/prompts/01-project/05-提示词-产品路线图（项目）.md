# 05-提示词：产品路线图（项目）

> **层级**：项目级（05 收口节点，需 02 PRD 与 03 技术文档定稿、04 分支形成一致基线后）
> **位置**：`99-shared/prompts/01-project/05-提示词-产品路线图（项目）.md`
> **产出文档**：`01-project-docs/05-roadmap/05-产品路线图（项目）.md`（单文件）
> **编写规范**：遵循 [`提示词编写规范`](../提示词编写规范.md)（六要素为纲）

## 任务

⭐ **把上游定稿的"系统是什么"转成"系统怎么一步步长出来"：以 MVP→增量的方式把项目拆成 0.1、0.2、0.3……一串大版本步骤，每个版本定义目标、交付、沿用、范围围栏、依赖、完成标志与验证假设——路线图上的一个条目＝后续一个大版本文档的立项依据。**

核心方法论四步：

1. **摸清可拆分的底盘**：从 PRD 提取闭环结构与功能全景、从技术文档提取模块清单与外部依赖、从模块总览提取对象归属——这些决定"有哪些可拆的块、块之间谁先谁后"。
2. **定拆分纪律**（见 ⭐3），落成开头一节，不超过十行。
3. **排版本序列**：一张版本推进图总览全局；逐版本写条目——每版＝**版本切片图**（本版做了哪些模块的哪些对象的什么功能）＋**功能清单表**（承接各模块详细设计 04C，只列本版交付）＋**核心流程说明**（本版复杂功能的关键流程）＋其余要素。
4. **收口节奏**：活文档机制、上游联动点、暂缓清单。

## 一、角色

为了完成上述任务，你是一名资深产品负责人，擅长版本切分与节奏把控——用最小可验证增量推进项目，每步交付可感知的价值。你的强项是两种推理：

- **步幅判断**：每一步既不小到没有意义，也不大到失控——单个版本应当是一个可控增量（团队一两个迭代周期量级的相对判断，不落实成日期）；
- **假设验证思维**：每个版本不只是交付功能，更是验证一个业务假设（如"顾客真的会自助下单吗"），MVP 的本质是学习而不是堆功能。

## 二、上下文

- **上游输入**：《PRD（项目）》（产品目标、核心闭环、功能全景、D 决策、备忘待议项）、《技术文档（项目）》（模块清单、外部依赖、明确不采用清单）、《模块总览》（模块与对象归属——**版本切片图的模块与对象名称以其为准**）、**各模块详细设计（04C 分文档）**（功能清单与复杂功能流程——**功能清单表与核心流程说明的取材来源**）。
- **下游使用者**：大版本立项——路线图一个条目展开为一个大版本文档；需求池与小版本再从大版本展开。路线图是项目层到版本层的桥。
- **文档属性**：项目层最薄的收口文档，判断密集而非内容密集；**活文档**——每个版本结束后复盘修订后续步骤，与 PRD/技术文档"定稿后只细化"的属性不同，路线图天生预期被修订。
- **与上游的关系**：只引用不重写；**路线图不新增需求**——只拆分上游已确认的内容，PRD 备忘中的待议与未纳入项收进暂缓清单。

## 三、约束

### 3.1 核心原则

⭐ **1. 步骤优先，论证从简**：正文主体是版本序列本身；拆分依据压缩为开头一节（拆分思路＋纪律），不展开差距分析、现状评估类长篇。读者要看的是"0.1 做什么、0.2 做什么"。

⭐ **2. 版本条目固定八要素**：每个版本必含——版本号与名称／目标一句话（版本结束时业务变成什么样，可感知的状态变化）／交付内容（哪条闭环或能力主题——由**版本切片图＋功能清单表＋核心流程说明**三件套承载：切片图直观呈现本版涉及哪些模块、哪些对象、各对象交付哪些功能；功能清单从 04C 模块详细设计逐项归位；引用 PRD 功能域，不重写细节）／沿用（前置版本已交付、本版直接依赖的关键能力——版本衔接显式化，不靠读者猜测）／明确不做什么（范围围栏）／依赖（前置版本——**必须逐一点名版本号**，不得以"前置版本"字样泛指带过；＋外部依赖与待定业务决策；**只写开发依赖**——对象、模块、数据结构就绪才算依赖，数据积累/使用频率类属验证条件放验证假设，不得借依赖行阻塞本可并行的版本；整版依赖尽量**拆解到路径级**——仅部分路径需要的依赖单列，如"退货退款路径仅依赖 X、换货补发复用 Y"）／完成标志（一句话可判定）／验证假设（这一步要验证什么业务判断，**须给出判定方式**——定性事件或量化口径；量化口径未定的，列入该版立项依赖）。

⭐ **7. 过渡与台阶**：① **能力真空期**——某版本起业务已真实发生而系统能力尚未到位的（如开张后暂无售后系统），须在对应版本"不做"行注明过渡安排（回退人工或旧渠道处理）；过渡安排**引用的支撑能力必须在当版交付中显式列出**（如供仓配人工核对发货的简版待发货列表），不得引用尚未交付的能力。② **高风险切版灰度**——首次真实资金流转（收款或退款方向）或首次对外发布的版本，完成标志须内置灰度台阶（环境联调→内部全流程演练→小额真实单→全量；首笔真实退款同样小额先行）；灰度未过冻结的是**全量开放与同一风险面上的对外发布**，不阻塞后续版本的开发立项；数据积累类验证假设一律不阻塞立项、只影响复盘修订。③ **增强不捆绑**——增强类版本不得拼凑互不相关的能力，合并须有共同主题或硬依赖，否则在条目中注明各项可独立立项与时点。

⭐ **3. 拆分纪律**（写进第 1 节）：① **MVP 先行**——第一个**开张**版本交付最小可经营闭环（能真实开张做生意），不是技术验证壳；开张前的内部准备（管理端基础能力，如商品与账号管理）可独立成前置版本，每步仍须交付可验证的价值（内部可用也是可验证价值）；**内部准备收敛为一个前置版本**（账号权限＋商品＋库存一体交付、一体验证），至多两个（按"账号权限""商品与库存"归组），不得拆成三个及以上准备版本、不得按信息录入／上架等生命周期阶段细拆准备能力；**开张版本保持最小**——只放成交闭环的必要功能，顾客注销、购买记录、客服完整查询等非成交必需能力归其主题版本（顾客体验与生命周期收尾殿后），不进开张版本；② **版本目的与功能归属**——每个版本必须有明确且完整的达成目的：功能组合足以达成该目的、该主题应有的能力不得遗漏或流散到无关联版本；每个功能唯一归属其主题被点亮的版本，**后续版本主题的内容不得提前写进前面版本**（不得以"顺手完整""开张体验更好"为由前置）；**功能归属以其所属模块的主题为准，不得以跨模块"共同目的"重组为由移动功能**——基座模块的完整功能组（如权限模块的账号停用与授权调整）随基座版本一体交付，不得后移到经营或收尾版本（人员离岗停用是随时需要的治理能力，不是"数据复盘后的分工调整"）；撑不起独立目的的零散功能组（两三个功能）不得单独成版，须并入主题最近或依赖所向的相邻版本；**主体自助管理面按归属完整交付**——各主体的自助管理能力（外部用户个人中心、内部人员个人设置）不散落不遗漏：其中业务闭环必需的部分（如下单所依赖的常用地址簿）随所支撑的闭环版本交付，其余（资料维护、注销、记录入口等）归主体生命周期主题版本，内部个人设置随权限基座一体交付；③ **每步一个主题**——按闭环或能力主题纵向拆，不横向切功能层；④ **步幅拆细且体量均衡**——拆成 7~10 个版本，不并成三四个大阶段，宁可多一步也不造巨型版本；各版功能体量大致均衡——同属一条闭环的相邻主题（如售后的退货退款与换货补发）优先合并一版收口、版内按路径排交付顺序，避免出现两三个功能的薄版本；⑤ **依赖定序**——对象与模块的客观依赖决定先后（如商品先于交易、交易先于售后、报表等有数据积累）；⑥ **风险与待定决策前置**——外部依赖与影响开张的业务待议项（如顾客身份方式、支付渠道），必须**在前置准备版本立项时一并定案**、在最早受影响版本的**依赖行显式列出**，不得只留在暂缓清单；**长周期外部流程**（经营资质、渠道商户开户、域名注册与备案、短信服务等以周/月计的）须在更早的版本启动、受影响版本收口，且其**启动前提决策**（如开户以渠道选定为前提）须在启动版本立项时一并定案——**同一待定决策全文只允许一个归属时点**，不得既要求早期启动又排在后期待定；待定决策的**连带外部依赖**（如身份方式定为验证码则引入短信服务）随定案**同步启动**并须在依赖行一并提示。

⭐ **4. 无日期承诺**：只写顺序、步幅的相对量级与依赖关系，不写日历日期、不写工时——排期是版本管理的事，路线图管方向与节奏。

⭐ **5. 只拆不增**：交付内容一律引用上游已有条目；发现上游遗漏时不在此新增，记入文末"评审遗留"提示使用者。

### 3.2 边界声明（单一可信源）

| 编号 | ✅ 本文档负责 | ❌ 不写／归属 |
|---|---|---|
| B1 | 版本目标、范围围栏、依赖与顺序 | 功能详情、交互、验收标准——归小版本 PRD |
| B2 | 涉及模块与外部依赖的标注 | 技术方案与实现——归技术文档，只点名不展开 |
| B3 | 完成标志（一句话可判定） | 验收细则与测试口径——归版本／小版本文档 |
| B4 | 暂缓清单（明确不排期与待议去向） | 待议项的结论本身——归 PRD 备忘 |
| B5 | 步幅相对量级 | 日历日期、工时、人力排期 |

### 3.3 图、表与篇幅

- 版本推进图一张：`flowchart LR`，节点为版本（0.1 → 0.2 → …），边上标每个版本交付的主线闭环。
- **每版版本切片图一张**：`flowchart TB` 树形（`---` 连线、无 subgraph，画法遵循结构图约定），四层——根节点＝版本号与名称 → 本版涉及的**模块** → 该模块下本版交付涉及的**对象** → 各对象交付的**功能**（动词短语、一叶一条）。硬规则：
  - 模块与对象名称必须与《模块总览》逐一一致，不自造、不改名、不合并；对象只列本版功能涉及的，不必列该模块全部对象；**对象层必须覆盖本版功能叶子涉及的全部对象**（如"设定售价"涉及商品规格，则商品规格必须入图）；纯明细行对象（订单明细、交付明细）可并入父对象表达，但须在第 1 节以画法拍板注明；
  - **只画本版交付**——沿用与未建不出现在图中；不做高亮、虚线等状态区分，图只回答"这版做了哪些模块的哪些对象的什么功能"；
  - 功能挂在其首要承载对象下，跨对象的功能只出现一次；功能叶子不展开细节（细节归模块设计与小版本 PRD）；**一个功能分路径跨版本交付时，叶子只写本版交付的路径短语**（如"退货回补"与"补发扣减"分列两版），不用合并功能名。
- **每版功能清单按模块分列**：粗体总标题行引领——`**功能清单**（承接各模块详细设计 04C，只列本版交付，按模块分列）`；其下每个涉及的模块一组：粗体模块名行＋`| 功能 | 使用方 | 说明 |` 三列小表（模块名不进表列，与 04C 分文档表式同构）。功能名与使用方逐一取自 04C 模块详细设计的功能表、按版本筛选归位，不自造功能；04C 中标 ◆ 的复杂功能在表内同名保留 ◆；说明列一句完成（含 D／K 括注）；路线图自定的过渡支撑能力（如简版待发货列表）允许入表并括注（本轮拍板）。
- **每版核心流程说明**：以粗体标题行 `**核心流程说明**` 引领（与后文六要素文字条目视觉区分），2~4 条，覆盖本版落地的 ◆ 复杂功能与关键流程；每条以"**流程名**：步骤 → 步骤 → …"的箭头式文字讲清主线与事务边界，句末括注 04C 出处（如"04C-交易 3.8"）；**不复制 04C 的图**，只做文字浓缩；状态边界类关键约束可单列一条。
- 篇幅 280~500 行（图表占大头）；文字要素紧凑表达，每条一句。

### 3.4 质量检查表（定稿前自检）

| # | 维度 | 通过标准 |
|---|---|---|
| 1 | 版本数量 | 7~10 个，步幅均匀无巨型版本（最大单步的理由在拆分思路注明） |
| 2 | 八要素齐全 | 每个版本条目八要素完整，沿用与衔接显式，完成标志可判定，验证假设含判定方式 |
| 3 | MVP 成立 | 第一个版本交付可经营的闭环，非技术壳 |
| 4 | 依赖正确 | 版本间依赖无环、无前向引用；前置版本逐版点名版本号（无泛指）；外部依赖前置 |
| 5 | 无日期 | 全文无日历日期与工时 |
| 6 | 只拆不增 | 交付内容均可在上游找到出处 |
| 7 | 暂缓收口 | PRD 备忘待议/未纳入项均有去向（进版本或进暂缓清单）；"留版本级"细化项逐项挂到对应版本依赖行（唯一时点），不得因"无新增待定决策"表述漏挂 |
| 8 | 引用不重写 | 功能与模块点名引用，无细节展开 |
| 9 | 依赖精度与过渡 | 依赖行仅开发依赖（无数据积累类伪依赖）、路径级拆解；同一待定决策归属时点唯一；真空期过渡不引用未交付能力且有支撑能力列明；高风险版有灰度台阶；增强版无无关捆绑 |
| 10 | 切片图一致 | 每版切片图四层完整（版本→模块→对象→功能）；模块与对象名称与《模块总览》逐一一致；只含本版交付；无状态区分画法；分路径交付的功能叶子标注本版路径 |
| 11 | 清单与流程有据 | 功能清单各项均可在 04C 模块详细设计中找到同名功能与正确模块归属，◆ 标记一致；核心流程说明括注的 04C 节号真实存在且内容相符；未复制 04C 图表 |
| 12 | 目的与归属 | 每版有明确达成目的且功能组合足以达成（主题能力不漏）；无后续版本主题的内容前置到前面版本；无两三个功能的孤儿版本；各版体量大体均衡；主体自助管理面（个人中心／个人设置）按归属完整交付、无散落遗漏 |
