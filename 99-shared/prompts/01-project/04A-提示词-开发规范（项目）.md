# 04A-提示词：开发规范（项目）

> **层级**：项目级（技术文档定稿后形成，随开发增量演进）
> **位置**：`99-shared/prompts/01-project/04A-提示词-开发规范（项目）.md`
> **产出文档**：`01-project-docs/04A-dev-standards/04A-开发规范（项目）.md`（单文件）
> **编写规范**：遵循 [提示词编写规范](../提示词编写规范.md)

## 任务

⭐ **把技术文档确定的工程基线沉淀为"代码怎么写"的通用工程约定：写机制不写业务、只写增量、单文件、底部增量区持续完善——对所有模块、所有人工与 AI 产出的代码同样适用，code review 有逐条依据。**

本文回答"怎么写代码"，与"写什么"（业务规则、模块契约、表结构——归技术文档、模块设计与版本文档）严格分离。

## 一、角色

为了完成上述任务，你是一名资深技术负责人，擅长把架构决策沉淀为代码规则、从具体业务实现中抽象出与业务无关的通用机制、在"手册不写但项目必须早定"的决策点上拍板。
你的强项是机制抽象（规则对任何模块同样适用）、增量判断（这条规则值得写吗）、共识拍板（给出确定选择而非留白）和规则可执行化（每条能判定遵守与否）。

## 二、上下文

- **上游输入**：已定稿的《技术文档（项目）》（技术栈清单、模块划分、关键技术决策）。规范的技术栈与规则必须与技术文档一致。
- **下游使用者**：所有写代码的人与 AI。小版本开发时同时读技术文档（架构方向）、开发规范（代码规则，本产出）、模块设计与小版本 PRD（本版本需求）。
- **承接原则**：技术文档定"为什么用、整体怎么分"，本文定"用的时候代码必须怎么写"；技术性质决策机制化落地，业务决策不复述；选型理由、架构、模块清单、概念模型只引用不重写。
- **范本参考（可选）**：仅当使用者明确指定范本时阅读，只参考组织方式；范本项目的业务性规则不能照搬。

## 三、约束

### 3.1 核心原则

⭐ **1. 写机制，不写业务**：每条规则对系统中任何模块同样适用，必须通过**业务替换检验**——把规则中出现的具体业务对象换成任何其他业务对象，规则仍成立；不成立的是业务规则，退回技术文档或模块设计。业务对象的具体状态、流程、字段约束、入口限制在本文出现为零条。

⭐ **2. 只写增量，通识以参照表引用**：总则放一张权威规范参照表（领域／规范名／一句话说明／链接，覆盖所用各栈＋接口语义＋协作，如语言社区手册、框架官方风格指南、数据库官方手册、HTTP 语义标准、大厂 API 设计指南、提交规范），正文不复述通识条目。本文只写四类增量：

- ① **项目工程约定**：仓库组织、模块机制、协作流程等不看文档猜不到的；
- ② **与通识不同的取舍**：写明"本项目不遵循通识某条，因为……"；
- ③ **技术决策的机制落地**：只取技术文档决策的**技术性质**并上升为通用机制（如"某回调事务内完成两类数据变更"→"涉及多方共用的关键数据的写操作，必须在同一事务内完成并保证幂等"），不写业务实例；
- ④ **无成文手册的业内共识**：手册不明写、跨会话选择不一致、选错代价高的起步拍板项（如 ID 策略、单号与主键分离、金额精度、时间时区、删除策略、回调幂等）。

每条规则过**双问检验**（能否消除跨会话的选择分歧？选错或不统一的代价是否高？）与业务替换检验。

3. **规则级深度（B3）**：一句话一条、可判定遵守与否；无完整代码、无字段值、无函数体；无"建议尽量"软约束；规则不带决策编号等追踪标记（溯源在技术文档，正文保持干净）。

4. **等级从简**：规则默认强制（违反即 review 不通过）；〔建议〕为唯一例外等级；〔惯例默认〕表示按通行做法拍板、团队可调——一律行内标注，不设汇总章节。

5. **结构固定**：总则 → 通用工程约定 → 后端 → 数据库 → 前端 → 部署与安全 → 维护说明 → 补充规范；各栈节按技术文档实际栈取舍，纯配置组件并入部署与安全或通用节。

6. **活文档：追加→成熟→上移**：初版主体只写当期确定的技术约定；后续约定按主题追加到"补充规范"增量区（一句一行，句末括注来源与版本），主题成熟后整体并入对应章节；追加前同样执行业务替换检验。

7. **推断标明（B4）**：无法从上游推出的约定按通行惯例形成确定判断，行内标注〔惯例默认〕。

8. **文档自包含（B6）**：正文不出现"图 N""据查"等来源引用（参照表的链接属于内容本身）；保留模拟标识（如适用）。

### 3.2 边界声明（单一可信源）

| 编号 | 本文档负责 | 留给下游或另存 |
|---|---|---|
| B1 | 代码层通用机制规则：结构组织、命名机制、全局数据共识、接口与错误、事务与一致性、安全与部署、协作 | 业务规则与业务实例、选型理由、架构与模块清单、概念数据模型，归技术文档与模块设计 |
| B2 | 跨栈通用约定与各栈机制规则 | 单模块的接口契约、表结构、状态机，归模块设计与小版本开发 |
| B3 | 可执行的规则（怎么算遵守、怎么算违反） | 具体业务实现、字段值、函数体，归代码 |
| B4 | 四类增量内容，通过双问检验与业务替换检验 | 通识条目的内化复述；范本项目业务性规则的照搬 |
| B5 | 〔惯例默认〕行内标注 | "待确认问题"单列；惯例默认的汇总章节 |
| B6 | 自包含正文与参照表 | "据查"式来源引用与提示词执行说明 |

其他位置涉及上述边界时引用编号，不另行重述。

### 3.3 思考过程（内部分析，不写入最终文档）

#### 第 1 段：承接技术文档

读出技术栈清单与全部关键技术决策；把决策分成技术性质（可机制化：架构形态、一致性策略、鉴权、留痕、第三方适配、部署与密钥）与业务性质（不进本文）两类；确定各栈节的取舍。

#### 第 2 段：机制推导

对每节问"写这类代码时，本项目的通用机制是什么"；把技术性质决策逐条去业务实例化，上升为机制表述；列无手册共识清单（ID、单号、金额、时间、删除、幂等等）逐项拍板；每条候选规则过双问检验与业务替换检验，不过的丢弃。

#### 第 3 段：简明收敛

通识只入参照表；规则一句一行；行数控制在 100～200；维护说明写清追加→上移流程；补充规范区按输入指示写格式说明或模拟示例。

### 3.4 质量检查表

| 检查维度 | 通过标准 |
|---|---|
| 机制纯度 | 全部规则通过业务替换检验；正文无具体业务对象的状态、流程、字段与入口规则（原则 1） |
| 增量纪律 | 通识仅以参照表引用；每条规则归入四类之一并通过双问检验（原则 2、B4） |
| 决策机制化 | 技术性质决策逐条有机制规则落地；业务决策零复述 |
| 可执行 | 一句一条可判定；无软约束；无追踪编号标记（原则 3） |
| 参照表 | 权威规范带一句话说明与链接，覆盖所用栈＋接口语义＋协作 |
| 结构与活文档 | 固定八节；维护说明含追加→上移流程；〔惯例默认〕行内标注、无汇总章节（原则 5、6） |
| 简明 | 100～200 行；超限先删低价值条目（原则 2） |
| 自包含 | 无来源引用；模拟标识保留（B6） |

## 四、格式（输出结构）

1. **总则** — 权威规范参照表（领域／规范／一句话说明／链接）；四类增量声明；等级说明（默认强制／〔建议〕／〔惯例默认〕）；业务替换检验声明。
2. **通用工程约定** — 仓库与模块（划分以技术文档为准、模块间只走暴露接口、依赖不成环）；全局数据共识（起步拍板项）；接口与错误（统一包体、错误码分段机制、异常与校验、脱敏）；事务与一致性（同事务原则、事务外交互、条件更新、流水）；协作（分支、提交、review 的惯例默认）。
3. **后端** — 分层职责、模块分包、鉴权与身份上下文机制、留痕机制、第三方对接适配原则、单号生成收口、测试要求。
4. **数据库** — 命名机制（以《术语表》的落库命名契约为单一可信源，正文只写机制不重抄具体表名；对象与表清单随技术文档）、审计字段、类型原则、防重唯一索引、迁移脚本、查询加速边界。
5. **前端** — 多工程机制、共用 API、API 层收口、配置注入、权限点驱动、金额换算、外部资源地址、状态管理。
6. **部署与安全** — 外部存储与转存、密钥与配置、网关与 TLS、端口边界、备份、与"明确不采用"清单的联动。
7. **维护说明** — 追加→成熟→上移流程；业务替换检验同样适用于追加；参照表链接失效时随维护更新。
8. **补充规范** — 增量区定位与追加格式；按输入指示可含明确标注的模拟示例条目。

把已定稿的技术文档全文粘贴在下方；如有补充的工程约束（指定规范、已有仓库习惯、合规要求）一并说明。

```

```
