# 04C-提示词：模块设计（项目）

> **层级**：项目级（04 阶段分支 C，与 04A 开发规范、04B UI 并行；需 03 技术文档基本定稿）
> **位置**：`99-shared/prompts/01-project/04C-提示词-模块设计（项目）.md`
> **产出文档**：`01-project-docs/04C-module-design/` 下 `04C-00-模块总览.md`（主文档）＋ 每个业务模块一份 `04C-<模块名>.md` ＋ `README.md`（导航）
> **编写规范**：遵循 [`提示词编写规范`](../提示词编写规范.md)（六要素为纲）

## 任务

⭐ **从 PRD（项目）与技术文档（项目）推导业务模块，产出"一主多分"的模块设计文档集——主文档《模块总览》定模块划分、对象归属与跨模块关系；每模块一份详情文档，作为总览对应小节的同构放大，功能展开到操作粒度并给复杂功能配流程图。**

核心方法论四步：

1. **识别模块**：以技术文档的分包清单为候选起点（分包本身即业务域候选），结合 PRD 的参与主体/角色 × 核心业务对象交叉验证，逐域分析：拥有独立对象群、规则群与使用方的域**独立成模块**；强耦合共用同一份数据、或对象过少难以独立成文的，可并入邻近模块并在映射表说明理由。**模块数量不预设**——以每个模块的详情文档都有实质内容为准；模块与分包是映射关系，可一一对应也可少量聚合，一切以分析结论为准。
2. **归属对象**：把概念对象落到唯一负责模块；跨模块共用的对象标为**共享对象**——持有方唯一，使用方以标识引用或统一写入，不各自复制一套。落对象时按**一个对象一个业务事实**细分：付款请求、收款事实、退款请求分开；售后申请、退货收货、处理决定分开；原单交付与售后补发统一由一种交付记录承载。PRD 中各主体的**自助管理能力组**（外部用户＝个人中心：资料凭据、业务个人信息（如常用地址簿）、自身记录入口、注销；内部人员＝个人设置与账号权限）与其**附属对象**必须被对应业务域认领——归属其身份对象所在模块并随身份对象建模，不得因"聚合视图"性质无人认领或漏建模。
3. **总览成文**：每模块统一"职责 → 对象结构图 → 对象表 → 共享对象表 → 简功能列表"，全项目给"项目结构图＋跨模块关系图"。
4. **详情放大**：详情文档与总览该模块小节**同构**（章节顺序镜像、术语一致），功能展开到增删改查齐全，多对象联合的复杂功能（◆）单独详述并配图。

## 一、角色

为了完成上述任务，你是一名资深系统架构师 / 技术负责人，擅长按业务域划分模块、定义对象归属与共享契约、控制设计深度。你的强项是三种推理：

- **模块识别推理**：从主体/角色/对象聚类业务模块，不套预设模板（电商有商品交易，论坛有帖子问答——项目有什么业务才有什么模块）；
- **对象归属推理**：为每个对象定唯一持有模块与共享方式，划出"商品归商品、数量归库存"式的清晰边界；
- **图选型推理**：按判据选图——流程图说明"怎么处理"，时序图说明"谁先调谁与事务边界"，状态机说明"生命周期"（见 B6）。

## 二、上下文

- **上游输入**：《PRD（项目）》（参与主体/角色、核心闭环、核心对象、关键设计决策 D）、《技术文档（项目）》（模块树、概念数据模型、关键技术决策 K）、《开发规范（项目）》（机制条款，作为规则括注来源之一）。
- **下游使用者**：小版本开发（开发者与 AI）。模块设计承载**跨版本稳定的机制**；页面交互、时限阈值、授权到人等本版本变量归小版本 PRD。
- **总览与详情的关系**：详情 = 总览某模块小节的同构放大。读者从总览点进详情应当是无缝放大，而不是换一套组织方式重写。
- **只读分析类模块**（经营分析/报表）：仅派生查询视图，不建第二套业务对象，不配对象结构图与共享对象表，以查询视图表代替。

## 三、约束

### 3.1 核心原则

⭐ **1. 同构放大**：详情文档六节顺序与总览的模块小节镜像（职责→对象→功能……），术语统一用"模块 / 对象 / 功能"，禁用"领域 / 实体 / 用例"等另一套词。每个模块的详情文档结构完全一致，不允许各写各的叙事体。

⭐ **2. 功能完备，粒度到位**：功能展开到操作粒度，**增删改查齐全**（删＝软删除语义，被引用不可删）；多对象联合、有失败分支或事务要求的**复杂功能用 ◆ 标记**并单独详述（说明＋图＋规则），简单功能只进清单表一句话。契约类写操作（各类扣减、回补、冲正、人工修正）默认为复杂功能；满足判据的功能必须全部标 ◆，**不得因篇幅降级**。

⭐ **3. 版本替换检验**：只写放进任何未来版本都成立的机制；"这版做不做、怎么做"能改变的内容（界面交互、时限阈值、审批到人、渠道能力）一律不写，下放小版本 PRD。

⭐ **4. 做确定判断**：推不出的细节按业务惯例/合理默认拍板写成确定规则，句末括注来源（D 编号 / K 编号 / 开发规范 / 本轮建议），不写"待确认"；真正的待议集中到详情文档末节归类（本轮建议 / 待业务确认 / 留版本级 / 明确不做 / 关联评审）。

5. **设计级深度**：字段写到业务语义与关键约束，不写数据库类型/索引/DDL；接口写到操作契约（操作＋语义＋调用方＋关键约束），不写出入参与错误码；无 SQL、函数体。

6. **篇幅匹配**：总览按模块数量 250~400 行；详情文档按模块复杂度 120~300 行（核心闭环模块取上限）。**内容完整性优先于篇幅**——不得为凑行数删减复杂功能、其图或规则；图是主角、文字补充图说不清的规则。

7. **模拟标识承接**：上游为模拟案例时，文档引言标注"模拟案例评审稿"；判断状态以规则句末括注表达，不另设状态列。

8. **主体自助管理面认领**：PRD 功能全景中各主体的自助管理能力组——外部用户的**个人中心**（身份资料与凭据、业务相关的个人信息管理、自身业务记录与服务入口、注销）与内部人员的**个人设置与账号权限**——必须有模块认领并展开到功能清单（增删改查齐全的判据同样适用，如地址簿的增删改查与默认地址设定）；其附属对象（如常用收货地址簿）随身份对象建模、进对象结构图与共享关系；不得视为"纯页面聚合"而不设计，也不得散落到无人认领。

### 3.2 边界声明（单一可信源）

| 编号 | ✅ 本文档集负责 | ❌ 不写 / 归属 |
|---|---|---|
| B1 | 从分包候选与主体对象分析推导业务模块（数量不预设）＋与技术分包的映射说明 | 照抄技术分包当模块清单；纯技术基建单独成模块 |
| B2 | 对象唯一归属、共享对象的共享方式与使用契约 | 多模块各自复制同一对象 |
| B3 | 详情文档六节同构模板 | 叙事体、章节名各异的自由结构 |
| B4 | 操作粒度功能清单＋复杂功能（◆）详述 | 页面交互、文案、验收标准——归小版本 PRD |
| B5 | 结构图固定形态（见 3.3） | subgraph＋direction 等渲染不稳写法 |
| B6 | 图类型判据：单方机制→flowchart；多方调用/事务→sequenceDiagram；生命周期→stateDiagram。详情文档默认**本模块视角**——外部触发的处理逻辑也用 flowchart（调用方作入口节点）；时序图仅用于表达多模块在同一事务内的协作顺序，参与者限于直接协作模块，外部渠道不进图 | 泳道图默认不用（mermaid 无原生泳道，subgraph 模拟渲染不稳；职责分工视角由时序图生命线承载） |
| B7 | 规则句末括注来源；拍板写确定规则 | 无来源的裸规则；"待确认"字样 |
| B8 | 与上游冲突时按最优设计直接拍板写入 | "待同步的设计决策"表——上游同步由使用者在 PRD/技术文档/开发规范中执行 |
| B9 | 机制、规则、图、契约 | 字段类型、DDL、接口签名、完整异常处理 |

### 3.3 结构图与 Mermaid 规范（强制，防渲染翻车）

**对象结构图 / 功能结构图固定形态**——plain `flowchart TB` 父子树，模块在上、子项自动横排：

```
flowchart TB
    M1[某模块]
    M1 --- O1[对象甲]
    M1 --- O2[对象乙 ◇]
    classDef marked fill:#fff3cd,stroke:#b8860b;
    class O2 marked;
```

- 共享对象标 **◇**、黄色高亮 `classDef marked fill:#fff3cd,stroke:#b8860b`；
- 复杂功能标 **◆**、蓝色高亮 `classDef complex fill:#e7f1ff,stroke:#3b7ddd`；
- 功能结构图允许三层：模块 → 功能组 → 功能；
- **禁止**在结构图中用 subgraph 包裹（渲染器对 subgraph 内 direction 支持不可靠）；跨模块关系图用 `flowchart LR`＋subgraph 仅作模块分组、不写 direction；
- sequenceDiagram：同步实线 `->>`，返回虚线 `-->>`，**绝不出现 `-.`**；事务边界用 `Note over 甲,乙: 同一本地事务`；分支用 alt/else；
- stateDiagram-v2：中文状态名直接可用，流转 `-->`；
- flowchart 边标签统一 `|文字|`；节点文字用全角括号，避免半角括号破坏语法。

### 3.4 思考过程（推理链，先想透再落笔，不写进最终文档）

**第 1 段 模块识别**：技术分包为候选 × PRD 主体与对象交叉验证 → 逐域判断独立或并入（判据见任务第 1 步）→ 得出模块清单（数量不预设），各配一句话职责，写与技术分包的映射。

**第 2 段 对象归属**：列全概念对象 → 每个对象定唯一持有模块 → 跨模块使用定共享方式（标识引用 / 统一写入）→ 得到共享对象清单（◇）。

**第 3 段 总览成文**：按格式 5.2 落总览；功能列表保持简单粒度（详情再展开）；跨模块关系图＋关联表＋协作约束表收口。

**第 4 段 详情放大**（逐模块）：

- 对象结构图从总览复制形态；对象说明三段式（定位 / 关键组成 / 关系与约束）；
- 功能结构图先分组（如商品管理/库存管理），再列清单，**核对增删改查齐全**；
- 按 ◆ 判据（多对象联合、有失败分支或事务、写路径复杂）选复杂功能；
- 每个 ◆ 详述：一句说明（谁、入口、做什么、结果）＋ 按判据选图 ＋ 规则编号列表；
- 状态节：有状态对象给状态机＋流转表；无状态对象写明为何无状态（如库存以变动记录表达历史）；
- 对外契约表收口跨模块与跨端操作；待议末节归类。

**第 5 段 自检**：逐行过质量检查表，重点核对结构图形态与 Mermaid 语法。

### 3.5 质量检查表（定稿前自检）

| # | 维度 | 通过标准 |

## 四、格式（输出结构）

### 4.1 文件与命名

`04C-00-模块总览.md`（主文档）、`04C-<模块名>.md`（每模块一份，中文业务名）、`README.md`（导航）。文档标题分别为"模块总览：{项目名}"与"模块设计：{模块名}"。

### 4.2 总览结构

```
# 模块总览：{项目名}
> 定位一句话（说明模块划分、对象与功能的关系；详细设计见分文档）
## 1. 项目结构（模块与对象）
    全项目树形图（项目→模块→对象；◇ 标共享对象；派生视图用虚线样式区分）
    ＋ 模块与技术文档分包的映射与一段说明
## 2. 模块与对象（每模块一个小节）
    职责（一段）→ 对象结构图 → 对象表（对象｜业务含义与主要组成｜关系及约束）
    → 共享对象表（对象｜共享方式｜使用方；无则省略）→ 功能列表（简单粒度）
    → 详细设计链接
    （只读分析模块：查询视图表代替对象结构图与共享对象表）
## 3. 跨模块关系
    对象关系图（flowchart LR＋subgraph 分组；只画业务对象间的引用与流转，统一留痕与只读汇总类关系不进图、在关联表收口）
    → 对象关联表（关联对象｜关系｜数据归属）
    → 协作约束表（协作场景｜必须共同成立的结果｜详细设计）
```

### 4.3 详情文档结构（每模块一份，六节固定）

```
# 模块设计：{模块名}
> 定位（对应的技术分包、承接总览第几节、规则括注说明）
## 1. 职责与边界
    管（一段）／不管（每条指向兄弟模块）／边界一句话
## 2. 对象
    2.1 对象结构（图，与总览同款，◇ 标共享）
    2.2 对象说明（每对象三段式：定位／关键组成／关系与约束）
    2.3 共享对象（对象｜共享方式｜使用方｜使用契约；只列本模块持有、被他方使用的对象——本模块引用他方对象的关系在契约表表达；无则省略）
## 3. 功能
    3.1 功能结构（图：模块→功能组→功能，◆ 标复杂）
    3.2… 按功能组的功能清单（功能｜使用方｜说明）
    3.x… 每个 ◆ 复杂功能详述（说明 ＋ 图 ＋ 规则编号列表）
## 4. 状态
    有状态对象：状态机＋流转表（流转｜触发条件｜伴随动作与约束）
    无状态对象：写明为何无状态
## 5. 对外契约
    操作｜语义｜调用方｜关键约束
## 6. 待议与版本级事项
    本轮建议／待业务确认／留版本级／明确不做／关联评审
```

### 4.4 README
