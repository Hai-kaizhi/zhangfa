# 开发路径与节点清单（提示词重建地图）

> 定位：重建提示词期间的路线图，也是重建完成后"哪个节点该有什么产出"的速查表。
> 职责划分、执行顺序见[项目工作流总览](../../项目总览.md)；节点编号遵循[提示词编写规范](./提示词编写规范.md)第六节的命名约定。
> 重建进度标记到节点；节点提示词完成并经范文验证后才算重建完成。

## 四大块职责与执行顺序

| 大块 | 目录 | 职责 |
|---|---|---|
| ① 项目级 | `01-project/` | 把想法变成项目基线：概念、产品需求、技术方向、规范、路线图 |
| ② 大版本 | `03-versions/major/` | 选择本阶段交付哪些能力，拆出开发顺序，形成需求种子 |
| ③ 需求池 | `02-requirement-pool/` | 需求导入、规划小版本、认领开工（严格串行的台账层） |
| ④ 小版本 | `03-versions/minor/` + `04-workspace/` | 细化需求、开发、验收、发布归档 |

说明：目录编号（02=需求池、03=版本）是稳定的目录命名，不代表执行顺序；执行顺序是 ①→②→③→④。工作区 `04-workspace/` 是小版本的开发中目录，发布后归档进大版本目录。`01-project-docs/术语表.md` 是全链业务命名的单一可信源（台账、无独立提示词；各层提示词按编写规范"业务命名承接纪律"读写它，新名定名即登记、改名走变更记录）。

## 按需节点的通用规则

1. **不生成独立文档 ≠ 省略必要工作。** 省略独立文档时，该工作并入既定环节：验证结果记入交付说明或验收记录，界面变化写进对应小版本 PRD。
2. **开工时声明。** 每个小版本开始时用几句普通话说明本次安排，例如：本次沿用现有 UI，不另写 UI 文档；验收按需求中的验收标准逐条执行。
3. **下游不强制补空文档。** 提示词遇到可选文档不存在时，从需求验收标准、现有规范或交付记录继续工作，不得为了"结构完整"补出空文档。
4. **按需转必办的触发条件。** 涉及复杂交互、多角色流程时，再展开独立的设计文档（如 UI）；测试不设独立文档节点，黑盒验收以小版本 PRD 验收锚为准。
