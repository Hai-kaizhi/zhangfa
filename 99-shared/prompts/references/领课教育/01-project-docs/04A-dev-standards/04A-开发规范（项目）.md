## 2. 通用工程约定

### 2.1 仓库与模块

- 采用单仓库多工程：后端应用、三个前端应用、数据库迁移脚本各占一个顶层目录，目录名与端名对应。
- 模块划分以《技术文档（项目）》的模块清单为唯一依据，不得在代码里新增未经登记的模块。
- 模块间只允许通过模块对外暴露的接口调用，禁止跨模块直接访问对方的表或内部类。
- 模块依赖必须无环：出现环时先调整职责边界，不得用延迟加载或事件绕过。
- 每个模块的对外接口集中定义在一处，供调用方与评审对照。
- 所用框架与库的版本以后端构建文件与各前端工程的依赖锁文件为唯一冻结处，文档不另维护版本清单；升级须整组回归后更新锁文件〔惯例默认〕。

### 2.2 全局数据共识

- 主键统一为数据库自增的 64 位整数，用于关联与索引。
- 对外业务编码与主键分离，编码由统一生成器产出，不与主键互相推导；编码格式以项目《术语表》登记为准。
- 金额一律以最小货币单位（分）用整数存储与计算，禁止用浮点数表示金额；展示层再换算。
- 时间一律以 UTC 存库，接口传 UTC 时间戳，展示按站点时区换算；禁止存本地时间字符串。
- 删除策略：业务上需要被追溯或被引用的数据一律逻辑删除（置删除标记），纯日志与临时数据可物理删除；逻辑删除的查询必须默认过滤。
- 布尔语义字段统一用"是／否"两值，禁止用空值表示"否"。

### 2.3 接口与错误

- 所有对外接口使用统一的响应包体：状态码、提示信息、数据体三段固定，不得为个别接口另起格式。
- 错误码按模块分段分配，每段内的码值在模块内唯一；错误码一经发布不得改含义，只能新增。
- 入参一律在入口处校验，校验失败返回参数类错误码，不进入业务逻辑。
- 业务失败用异常抛出并在统一处理处转换为错误码，禁止在业务代码里直接拼装响应。
- 对外响应与日志中，凭据类、联系方式类字段必须脱敏或省略。

### 2.4 事务与一致性

- 涉及多方共用的关键数据的写操作必须在同一数据库事务内完成，且保证可重复执行不产生副作用。
- 事务内禁止调用外部服务与远程接口；必须先落本地状态再在事务外发起外部交互。
- 外部回调的写操作必须幂等：以外部单据号去重，重复回调返回相同结果。
- 并发修改同一记录时使用条件更新（带版本或状态条件的更新语句），受影响行数为零即视为冲突并让调用方重试或失败。
- 关键状态变更必须留痕（谁、何时、从什么状态到什么状态），留痕与状态变更同事务写入。

### 2.5 协作

- 分支〔惯例默认〕：主干保持可发布，功能与修复在短分支上完成，合并前必须通过 review。
- 提交〔惯例默认〕：提交信息遵循 Conventional Commits，一次提交只做一件事。
- review：逐条对照本文与模块设计；规则类问题必须改代码而不是改文档。

## 3. 后端

- 分层职责固定为接口层、业务层、数据访问层三层：接口层只做参数校验与出入参转换，业务层承载规则与事务，数据访问层只做数据读写。
- 业务层不得直接依赖接口层对象，层间传递用明确的输入输出对象，禁止把数据库实体直接返给接口层。
- 分包按模块优先、层次次之：每个模块一个顶层包，其下再分三层；跨模块调用只走对方暴露的接口包。
- 鉴权与身份上下文机制：请求进入时解析登录态得到身份，身份信息放入请求级上下文供业务层读取；业务层不得自行解析凭据；按端隔离校验，不同端的登录态互不通用。
- 权限校验收口为注解声明，禁止在业务代码里散写权限判断。
- 留痕机制：所有状态变更与审核类操作经统一的留痕组件写入，禁止各模块自己拼留痕表。
- 第三方对接适配原则：外部服务一律经适配接口访问，业务层只依赖接口；适配实现必须设置超时，失败时按可重试与不可重试分类处置。
- 单号生成收口为唯一生成器，禁止各模块自行拼编码。
- 测试要求〔惯例默认〕：业务层规则须有单元测试；涉及状态流转与金额计算的必须有测试；接口层不写重复的校验测试。

## 4. 数据库

- 表名采用模块前缀＋小写下划线命名，表清单与所属模块以项目《术语表》登记为准，禁止在代码里新建未登记的表。
- 字段名统一小写下划线；外键字段一律为「被引用对象名_id」形式。
- 每张业务表必备审计字段：创建时间、更新时间；需要追溯的操作另留操作人与操作时间。
- 状态类字段统一命名为 status，取值用短字符串常量，禁止用魔法数字。
- 类型原则：主键与外键用 64 位整数；变长文本按实际长度上限选择，禁止一律用最大长度；金额用整数分；时间用数据库时间类型而非字符串。
- 防重靠唯一索引：业务上不允许重复的数据（如业务编码、外部单据号）必须建唯一索引，不得只靠应用层查询判断。
- 迁移脚本按版本号顺序编号、只增不改：已执行的脚本不得修改，修正用新脚本。
- 查询加速边界：只对实际出现在查询条件与排序中的列建索引；禁止为"可能用到"建索引；多表关联的查询必须能说清走哪个索引。

## 5. 前端

- 多工程机制：三个前端应用各自独立工程、独立构建与发布；跨应用共享的只有接口约定与设计令牌，不共享业务代码。
- 共用 API：接口地址、请求方法、出入参类型集中定义在各工程的 API 层，业务组件不得直接写请求地址。
- API 层收口：请求统一经封装的客户端发出，由其负责登录态注入、错误码统一处理与提示，组件内不得重复实现。
- 配置注入：后端地址与环境相关的开关由构建期环境变量注入，禁止硬编在源码中。
- 能力点驱动：机构端界面按登录账号的角色决定可见与可操作项，前端隐藏不作为安全边界，服务端必须再校验。
- 金额换算：前端只接收最小货币单位的整数，展示时统一经公共格式化函数换算，禁止各处自行乘除。
- 外部资源地址：外部服务（视频、存储）的地址一律由服务端下发，前端不拼装、不缓存服务商地址。
- 状态管理〔惯例默认〕：仅跨页面共享的状态入全局存储，页面内状态留在组件内。

## 6. 部署与安全

- 外部存储与转存：应用不落地保存用户上传的大文件，一律直传或转存至外部存储，应用只保存引用与元信息。
- 密钥与配置：密钥、数据库口令、第三方凭据一律经环境变量或配置中心注入，禁止写进仓库、镜像与文档。
- 网关与 TLS：对外一律 HTTPS，证书在入口处终结；应用只监听入口转发来的请求。
- 端口边界：数据库与缓存的端口不得对公网开放，只允许应用所在网络访问。
- 备份：数据库按固定周期做全量备份并定期验证可恢复；备份文件与密钥分开存放。
- 与技术文档的"明确不采用"清单联动：清单中的技术不得因临时方便被引入（含其轻量替代物）；确需引入时先更新技术文档。
