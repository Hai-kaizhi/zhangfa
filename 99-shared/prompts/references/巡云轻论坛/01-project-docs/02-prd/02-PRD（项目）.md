# 产品需求文档（PRD）：巡云轻论坛

> 定位与决策状态：本文是项目级产品需求总纲，用于立项汇报与整体讲解——读者读完能复述这个产品为什么做、给谁用、由什么组成、业务怎么跑通、关键为什么这样定；功能的详细规则、界面交互、数据字段与指标口径由大版本与小版本文档逐步细化，本文不预写。上游为模拟案例材料，模拟性质予以保留；文中信息状态以"已确认／建议默认／推断／待议／期望"就地标注，推断与建议默认汇总于文末备忘。

## 1. 产品概述

### 1.1 背景与目标

**现状问题（已确认）**：讨论散落在聊天群里，刷过去就没了，想找以前的讨论没有地方可翻、可搜；遇到具体问题发问常常只有零散回应，会答的人得不到回报；内容质量参差，经营方缺少审核、举报与违规处置的固定通道；新人来了留不住，缺少积分、等级、身份这类可积累的东西；内容与互动有多少、谁在活跃，没有统一的地方可看。

**产品目标**：做一个自建自营的社区论坛，把「论坛讨论」和「悬赏问答」放进同一个站——日常话题在论坛里聊，卡住的具体问题发悬赏问答，谁答得好谁拿悬赏；账号、内容、数据由经营方自己掌握，不依赖第三方平台。用统一的积分与等级把成员行为与可见权限连起来，用审核、举报与违规处置保证公开内容质量，用浏览量等数据支撑运营调整，让内容生产、互动沉淀、治理保障与激励留存互相带动。

**成功标准（建议默认，定性表达）**：成员能完整走通"注册 → 发帖 → 互动 → 提问 → 作答 → 采纳"的路径；站内内容可被搜索到并被后来人复用；审核、举报与违规处置可执行、有结果；经营方能看到内容与互动的基本情况并据此调整规则。量化口径留版本级文档定义。

### 1.2 产品定位与形态

**一句话定义**：面向社区成员的论坛与悬赏问答站点，由本社区经营方自建自营、自主治理，成员在其中沉淀讨论与问答，经营方在其中掌握内容与数据（已确认）。

**商业模式与形态**：自建自营的单一站点，不接入多主体经营，不设平台抽成（已确认）；账号、内容、数据留存于站点自身，不依赖第三方平台（已确认）。

**端构成与职责**：

| 端 | 使用者 | 职责 |
|---|---|---|
| 电脑端网页 | 访客、会员 | 浏览、搜索、发帖、提问、作答与互动的主阵地 |
| 手机端网页 | 访客、会员 | 与电脑端同一站点自适应，随时浏览与参与 |
| 管理后台 | 站长、运营人员、版主 | 站点规则与结构设置、会员与内容管理、审核与治理、数据查看 |

电脑端网页与手机端网页为同一站点的自适应形态，前台内容可被搜索引擎收录（已确认）；管理后台独立于前台，仅经营方与版主使用（已确认）。

## 2. 参与主体与角色

**主体划分（承接概念文档）**：

| 主体 | 所属端 | 定位 | 包含角色 |
|---|---|---|---|
| 用户主体（社区成员） | 电脑端网页 / 手机端网页 | 产品最终服务的使用方：在站内浏览、搜索、发帖、提问与作答的人群 | 访客、会员 |
| 经营主体（站点经营方） | 管理后台 | 对站点经营结果负责的自营方："我们"——承担经营决策、组织分工与人员账号安排，其内部团队执行日常业务与内容治理 | 站长、运营人员、版主 |

**各角色的特征与典型场景**：

- **访客**：未注册的浏览者，进站按板块逛内容、按关键词搜索话题与答案；在需要发帖、提问、作答、点赞收藏或私信时被引导注册登录（推断：浏览不需要先注册，参与互动需要）。
- **会员**：站点的内容生产者与消费者，同时在"讨论"和"问答"两条线上活动——既发话题、评论回复，也提问、作答、采纳最佳答案；靠积分与等级积累身份，用私信、通知提醒、关注与粉丝与他人往来（已确认）。
- **站长**：经营的组织与决策者，掌握管理端账号与角色授权、板块与标签结构、等级与积分规则、审核策略与敏感词、全站设置，并通过数据复盘站点运转（已确认）。
- **运营人员**：站点日常业务的执行者，负责板块、标签与运营内容的维护，会员与内容的查询维护，举报的受理与跟进，积分与等级规则的运营（已确认）。
- **版主**：内容治理的执行者，对话题、问题、答案与评论执行先审后发的审核，处置举报，对违规内容与账号执行删帖、禁言、封号（已确认）。

**共性的工作方式**：经营方内部常见于小团队，一人可持多个角色，版主可兼任运营人员（推断：输入按"站长与运营人员""版主与内容管理员"并列表述，按一人可多角色处理）；访客注册后即成为会员，会员不因积累等级或声望而改变身份类别（已确认，等级只影响权限与展示，不派生新角色）。

## 4. 核心业务闭环

**闭环总览**：五条闭环互相咬合——开站准备定下结构与规则，讨论发帖与悬赏问答是内容生产的两条主线，会员成长把行为沉淀为身份与权限，内容治理保证公开内容质量并反哺规则调整。

```mermaid
flowchart TD
    A[开站准备：板块与规则就绪] --> B[讨论发帖：话题沉淀与互动]
    A --> C[悬赏问答：提问作答与采纳]
    B --> D[会员成长：积分升级与权益解锁]
    C --> D
    B --> E[内容治理：审核与违规处置]
    C --> E
    E --> F[经营方调整规则]
    F --> A
    D --> B
```

**闭环一：开站准备（站长与运营人员，开站之前）**。站长先规划站点结构、建立板块与标签，再设定等级与积分规则，明确成员成长的计分口径；运营人员配置审核策略与敏感词，决定哪些内容需要先审后发，并完成全站基础设置，站点随后对外开放。闭环结束于站点开放，此后结构与规则随运营复盘持续微调。

```mermaid
flowchart TD
    A[站长：建立板块与标签] --> B[站长：设定等级与积分规则]
    B --> C[运营人员：配置审核策略与敏感词]
    C --> D[运营人员：完成全站基础设置]
    D --> E[站点开放，内容待生产]
    E --> F[经营方：按运营复盘微调结构]
    F --> A
```

**闭环二：讨论发帖（会员发起、版主审核，内容生产主线）**。会员在板块内发表话题或继续编辑自己的话题，提交后进入审核；版主审核通过后话题公开可见，其他会员评论回复、点赞收藏，作者收到互动提醒并可继续维护自己的内容。若被驳回，会员可看到原因并修改后重新提交；话题按可见权限设置对不同会员开放。

```mermaid
sequenceDiagram
    participant 会员
    participant 前台站点
    participant 版主
    participant 其他会员
    会员->>前台站点: 在板块发表话题或编辑后重新提交
    前台站点->>版主: 待审核话题进入审核队列
    alt 审核通过
        版主->>前台站点: 通过，话题公开可见
        前台站点->>其他会员: 话题出现在板块列表与搜索结果
        其他会员->>前台站点: 评论回复、点赞、收藏
        前台站点->>会员: 通知互动结果
    else 审核驳回
        版主->>前台站点: 驳回并填写原因
        前台站点->>会员: 通知驳回原因，等待修改
    end
```

**闭环三：悬赏问答（提问会员与答题会员协作，经营核心闭环）**。会员把卡住的问题发出来并设置悬赏积分、追加补充条件；问题与答案经版主审核通过后，其他会员作答与补充，提问人从回答中采纳最佳答案，悬赏积分结算给答题人，问答沉淀为可搜索的答案库。若悬赏到期无人被采纳，按规则退回提问人（建议默认，规则数值留版本级）。

```mermaid
sequenceDiagram
    participant 提问会员
    participant 前台站点
    participant 版主
    participant 答题会员
    提问会员->>前台站点: 发表问题并设置悬赏积分
    前台站点->>版主: 待审核问题进入审核队列
    版主->>前台站点: 审核通过，问题公开
    loop 悬赏有效期内
        答题会员->>前台站点: 作答、补充与回复
        前台站点->>版主: 答案进入审核，通过后公开
    end
    提问会员->>前台站点: 采纳最佳答案
    前台站点->>答题会员: 悬赏积分结算到账并发出通知
    前台站点->>前台站点: 问答沉淀为可搜索的答案库
```

**闭环四：会员成长（运营人员策划、会员参与，循环型闭环）**。运营人员按站点需要设定积分与等级规则，会员在发帖、回帖、被采纳的过程中获得积分、逐级上升，等级与积分带来更多可见内容与权限；运营人员结合浏览量等数据调整规则，让激励持续有效。

```mermaid
flowchart TD
    A[运营人员：设定积分与等级规则] --> B[会员：发帖、回帖、被采纳]
    B --> C[会员：积分累积]
    C --> D[会员：等级上升]
    D --> E[会员：解锁更多可见内容与权限]
    E --> B
    E --> F[运营人员：结合数据调整规则]
    F --> A
```

**闭环五：内容治理（版主执行，运营与站长兜底）**。话题、问题、答案与评论先审后发；公开内容接受会员举报，版主核实后处置，对违规内容与账号执行删帖、禁言、封号，运营人员跟进结果并调整规则。举报处置与违规处置的结论通知被处置一方，保证处理有入口、有结果。

```mermaid
sequenceDiagram
    participant 会员
    participant 版主
    participant 运营人员
    版主->>会员: 内容先审后发，驳回时说明原因
    会员->>版主: 举报违规内容并说明理由
    版主->>版主: 核实举报
    alt 举报成立
        版主->>会员: 对违规内容与账号处置，删帖、禁言或封号
        版主->>运营人员: 同步处置结果
        运营人员->>运营人员: 跟进并调整规则与词表
    else 举报不成立
        版主->>会员: 驳回举报并说明理由
    end
```

## 6. 关键设计决策

版本细化时的遵守方式：本章各条为跨版本稳定规则，大版本与小版本在细化功能时遵守；若后续版本与此处冲突，以本章为准，本章不随版本重复表述。

**D1 载体选择——网页优先，不做原生应用**：选择以电脑端网页与手机端网页承载全部前台能力，同一站点自适应，管理后台独立成端；不做原生 App 与小程序。理由：前台内容需要能被搜索引擎收录以吸引站外流量（已确认），且自建自营的站点希望账号、内容、数据自有（已确认），网页形态最贴合；不做应用可省去多端发布与审核的长期成本（推断）。跨版本规则：前台能力一律在网页端提供，不因后续版本引入应用而改变前台功能边界。

**D2 经营模式选择——自建自营的单一站点**：选择单一经营方运营一个站点，不设平台主体、不做多站点与多租户。理由：输入为自建自营定位，账号、内容、数据由经营方自己掌握（已确认）；单站点使规则、治理与账号体系保持简单一致。

**D3 内容运行方式选择——先审后发**：选择话题、问题、答案与评论均以审核通过为公开前提，驳回时说明原因并允许修改后重新提交。理由：经营方要保证公开内容质量、要能控得住（已确认），审核是治理闭环的入口。跨版本规则：任何前台内容的公开都以审核结论为准，审核结论与原因留痕。

**D4 激励方式选择——积分与等级驱动，悬赏以积分结算**：选择以积分累积与等级上升作为成员成长的主线，悬赏问答用积分结算，本期不引入真实资金（已确认不作为范围）。理由：输入的成长闭环以"涨积分、升等级、解锁权限"表述（已确认），积分可直接与可见权限挂钩，且无需引入支付相关依赖。跨版本规则：悬赏与激励的媒介保持为积分，除非后续重新决策。

**D5 权限组织方式选择——按角色授权、一人可多角色**：选择管理端按角色授权（站长定义角色与能力范围并分配给账号，账号可停用），会员侧的开放程度由等级与积分决定。理由：小团队常有一人多岗（推断），角色模板比逐人配置更易维护；会员的可见权限需要与成长体系挂钩（已确认）。跨版本规则：能力的授予只经角色，不针对单个账号定制（除停用外）。

**D6 内容归属与处置选择——会员可维护自己的内容，经营方握有最终处置权**：选择会员可编辑、删除自己的话题、评论、问题与答案，经营方在违规时可删除内容并对账号执行禁言或封号。理由：会员需要修改与撤回自己的表达（推断），而治理闭环要求经营方有明确的处置手段（已确认）。跨版本规则：处置动作（删帖、禁言、封号）以经营方判断为准，处置结果通知当事人。

**D7 站内沟通方式选择——站内私信与通知提醒，不做即时会话**：选择以站内私信承载会员往来、以通知提醒承载结果送达，不引入外部通讯工具与实时聊天会话。理由：输入将私信与通知提醒列为必备（已确认），其诉求是站内往来与结果可达；实时会话未在输入中出现（不纳入）。跨版本规则：站内消息仅在站点内产生与查看。

**D8 数据使用方式选择——运营数据用于规则与内容调整**：选择以浏览量等内容热度数据与互动情况作为运营调整的依据，具体统计口径与呈现留版本级定义。理由：输入要求"浏览量统计"与运营复盘（已确认），但未给出指标口径（留下游）。

## 7. 备忘
