# 04A-开发规范（项目）：好物商城

> 本文把技术基线沉淀为"代码怎么写"的通用工程约定：写机制不写业务、只写增量、单文件、底部增量区持续完善；对所有模块、所有人工与 AI 产出的代码同样适用，code review 有逐条依据。上游为模拟案例材料，模拟性质予以保留。

## 2. 通用工程约定

- 仓库为单仓多工程：`apps/`（商城端、管理端前端工程）、`server/`（后端单体）、`deploy/`（编排与配置）、`docs/`（文档镜像）各占一个顶层目录。〔惯例默认〕
- 后端模块间只经模块对外暴露的服务接口调用，禁止跨模块直连他模块的数据表。〔惯例默认〕
- 模块依赖必须无环；构建工具校验失败即阻断合入。
- 主键与业务单号分离：数据库主键仅内部使用，对外展示与跨单据关联一律用业务单号。
- 金额、优惠面额等一切货币量以整数（分）参与运算与存储，任何层不得出现浮点金额。
- 时间统一存储东八区 `datetime`，容器时区固定 `Asia/Shanghai`；代码中不做隐式时区换算。
- 删除策略：业务档案默认逻辑删除；支付、退款、收支类单据只追加不修改不删除。
- 接口响应统一包体 `code`（业务码）、`message`、`data`；HTTP 状态码仅表达传输与鉴权层语义。〔惯例默认〕
- 业务错误码按模块分段占用号段，新增模块先在错误码登记处申领号段。
- 入口层做参数校验（注解式），业务层不重复判空；校验失败走统一异常处理出口。
- 涉及多方共用的关键数据的写操作，必须在同一数据库事务内完成，并保证可重放幂等。
- 事务内禁止外部调用（支付、HTTP、发信）；外部交互一律移到事务提交后。
- 并发写共享数据必须走条件更新（状态前置条件或版本号），禁止"读—改—写"裸写。
- 外部回调以业务单号防重，重复回调直接返回既定结果。
- 分支模型：`main` 单长期分支＋短生命周期特性分支；提交信息遵循 Conventional Commits。〔惯例默认〕
- 合入前必须 review；AI 产出的代码与人工代码同规同检。
- 日志不得输出敏感字段（口令、支付凭据、完整手机号），一律经统一脱敏工具处理后打印。

## 3. 后端（Java · Spring Boot）

- 分层职责：入口层（HTTP/参数校验/鉴权声明）→ 服务层（业务）→ 数据访问层（持久化）；业务逻辑不得写在入口层。
- 模块按业务域分包 `com.haowu.<module>`，横切能力收公共基座包；禁止跨包的私有类引用。
- 身份由统一鉴权过滤器解析并注入身份上下文；业务代码只从上下文取身份，不信任请求参数携带的身份字段。
- 令牌按端分受众（商城端/管理端互不通用），校验失败的响应码全局一致。
- 关键写操作（改状态、改配置、动钱）统一经留痕机制记录操作者、时间与动作；留痕与业务同事务。
- 第三方对接一律经适配层：端口接口定义在业务域内、渠道实现放适配包；外部调用必须显式设置超时，重试必须有界且幂等。
- 业务单号生成收口到公共单号组件，任何代码不得自行拼接单号。
- 服务层核心逻辑与状态流转、外部回调处理必须有单元测试；测试不依赖真实外部渠道（用替身）。
- 延时与定时任务统一注册到调度组件且任务名全局唯一；任务实现必须可重入、幂等。

## 4. 数据库（MySQL）

- 表名 = 模块前缀 + 语义（`auth_` 权限、`cust_` 顾客、`prod_` 商品、`trade_` 交易、`mkt_` 营销、`cms_` 内容、`svc_` 服务、`rpt_` 报表、`sys_` 公共）；表清单与对象名以《术语表》为单一可信源。
- 每表必带审计三字段 `created_at`、`updated_at`、`deleted`。
- 类型原则：金额用整型存分；状态存枚举字符串值；布尔语义用最小整型；不使用数据库外键约束，关联完整性由服务层保证。〔惯例默认〕
- 业务防重一律建唯一索引（如同主体对同对象的唯一持有），不以查询判重代替约束。
- 查询语句显式列出字段，禁止通配整行返回。
- 表结构变更只走版本化迁移脚本，禁止手工改库；迁移脚本只增不改历史。
- 查询加速先用索引（含必要组合索引），当前不引入缓存组件；需要时先修订技术文档决策再引入。
- 大字段（富文本）与索引表分离存储，不让主表查询携带大字段。〔建议〕

## 5. 前端（Vue 3）

- 商城端与管理端为两个独立前端工程，互不引用源码；共用类型与工具函数放共享包。〔惯例默认〕
- 所有 HTTP 调用收口到各工程的统一 API 层，组件不得直接发起请求。
- 环境差异（API 基址、图片基址）经环境变量注入构建，代码不硬编地址。
- 管理端菜单与按钮挂权限点标识，与后端能力点字符串同名同源；界面不自行判断角色。
- 金额展示统一经格式化工具（分 → 元），组件内不得手写换算。
- 图片等外部资源地址统一经资源前缀拼接函数生成，不散落完整 URL。
- 状态管理按"服务端数据 vs 本地交互态"分开组织；服务端数据以请求层为唯一入口。
- 访问控制统一在路由层声明，页面组件不做独立的权限判断。

## 6. 部署与安全

- 外站图片等外部资源一律转存到本地图片存储后引用，不直接外链。
- 密钥（支付商户凭据、数据库口令）只经环境变量或密钥文件注入，禁止写入仓库与镜像。
- Nginx 为唯一外部入口（80/443），应用与数据库端口不对公网暴露。
- TLS 在 Nginx 终结，内部转发走内网明文。
- 数据库每日全量备份并保留至少 7 天；备份结果纳入部署健康检查。〔惯例默认〕
- 引入技术文档"明确不采用"清单内的技术前，必须先修订技术文档决策记录，再动代码。
- 生产镜像使用固定版本标签并与发布记录一致，禁止 `latest` 标签上生产。

## 7. 维护说明

- 追加：新约定按主题一句一行追加到"补充规范"区，句末括注来源与版本。
- 成熟：某主题条目稳定后整体上移并入对应章节，原增量区清空该主题。
- 追加条目同样执行业务替换检验与双问检验（能否消除跨会话分歧、选错代价是否高）。
- 参照表链接失效时随维护更新链接，不删条目。
