# 章法的维护与贡献

章法现阶段以文件夹工作流、提示词和文档为主要维护对象，按实际使用中发现的问题持续调整。欢迎反馈具体使用经历，也欢迎改进说明、提示词和示范。

## 1. 怎样反馈问题

在 [GitHub Issues](https://github.com/Hai-kaizhi/zhangfa/issues) 中说明遇到的问题。反馈尽量给出文件位置、当前节点和实际表现，方便判断问题出在输入、提示词、产出还是台账操作。

可以参考这个格式：

```text
问题位置：文件路径或节点名称
使用情境：正在做什么，上游材料是否齐备
输入摘要：与问题有关的材料和已确认决定
实际结果：出现了什么，可附相关片段
预期结果：应该怎样承接或执行
复现方式：再次执行时怎样看到同一问题
```

也欢迎反馈使用成本，例如某个文档重复、节点边界难懂、按需条件不清。说明具体情境，比单纯增加或删除一类文档更有助于改进。

## 2. 修改不同内容时遵循什么

| 修改对象 | 修改依据 | 完成时核对 |
|---|---|---|
| 对外说明和导航 | 当前真实形态与已有文件 | 定位准确、相对链接有效、使用步骤可执行 |
| 提示词 | [提示词编写规范](../99-shared/prompts/提示词编写规范.md) | 标准结构、输入边界、产出位置、命名承接和质量检查要求 |
| 节点顺序或产出路径 | [开发路径与节点清单](../99-shared/prompts/00-开发路径与节点清单.md) | 相关提示词、导航与下游输入同步一致 |
| 台账规则 | [AGENTS.md](../AGENTS.md) 与入池、认领、发布提示词 | 操作入口、状态迁移、追加历史与归档关系一致 |
| 模拟示范 | 对应上游模拟材料 | 保留模拟性质，命名和验收锚沿用上游 |

提示词保持行业通用。具体项目名称、业务对象和实例放在项目输入或示范项目中，避免通用规则依赖某个案例。

## 3. 缺陷怎样回流

先判断问题的性质：单次遗漏、错别字或排版错误属于文档级问题，可以就地修正；规则含糊、共性结构缺失、上下游承接要求不足属于提示词级问题，需要修提示词再验证。

提示词改进沿用以下过程：

```text
手修定标 → 反推提示词 → 净室生成 → 独立审核
```

先明确满意产出应有的结构和粒度，再把改进转成通用提示词规则。重新生成时，只提供当前节点“输入”章点名的材料，禁止读取评审材料；示范正文只有使用者明确指定对应单篇时才取用。

执行方式按 `AGENTS.md` 分级：默认由主智能体直接生成；主智能体在当前会话已接触评审材料或做过缺陷回流、单节点包含多份大文档、或需要隔离大任务时，再使用子智能体。审核由主智能体亲自完成，直接生成也应全量过检。

## 4. 怎样说明验证结果

提交修改时，简要说明具体问题、修改后的行为、影响哪些节点，以及怎样验证。文档检查至少包含结构计数、上游逐字锚比对、编号连续和命名残留检查；有 Mermaid 图时，用 Chrome 与 `mermaid@10` 渲染，核对 SVG 数量并检查 `Syntax error`。

如果改动影响认领、发布或归档，应核对相关台账是否一致。模拟演练、真实测试和真实发布分别表述，以实际完成的验证为准。

提示词级修改的验证需要证明改后的提示词能生成符合要求的产出。仅手动把某一篇产出修好，仍不足以验证提示词问题已经解决。

## 5. 更新自己的项目副本

使用者项目中的原始材料、术语表、需求池、版本记录和归档属于该项目。取用上游方法更新时，先比较变化，再合并适合自己的规则，核对相关输入和已有产出是否仍然一致。

改名按术语表的变更记录处理；需求和版本历史按既定台账规则保存。若调整目录或节点，应同步修正相关路径和上下游依赖。

## 6. 维护节奏与许可

章法目前由作者持续维护，优先处理实际使用暴露的问题，没有固定发布周期或完整软件的交付时间。反馈会作为改进依据，具体是否采纳取决于适用范围和维护取舍。
