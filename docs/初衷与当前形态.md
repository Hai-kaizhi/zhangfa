# 章法的初衷与当前形态

章法（PlayBook）的目标，是把 AI 辅助研发中容易散落在对话里的流程、规则和项目记录，整理成一套可以持续使用的方法。当前采用 Markdown 文件夹形式维护，并继续根据实际使用迭代。

## 1. 最初想解决什么问题

使用 AI 做项目时，一次对话可以生成很多文档和代码，但项目需要跨越很多次对话。哪些内容已经确认，哪些还只是建议，接下来该做什么，做完怎样验收，都需要有稳定的记录。

章法关注的是这些持续协作的问题：

- 内容有存放位置，长期基线和开发中材料能够分开。
- 各阶段有输入和产出，上游决定能够传到下游。
- 业务名称、需求范围和验收标准保持一致。
- 认领、交付和发布有记录，重新打开项目时能够查到进度。

“让 AI 研发，照章办事”表达的就是这个目的：先说清规则与完成标准，再让人和 AI 据此推进，并检查结果。

## 2. 为什么从软件调整为文件夹

我最初把章法作为一个软件项目来管理，希望通过软件组织流程和项目状态。实际使用后，管理效果没有达到自己的预期；与此同时，我对流程、提示词和文档的理解还在变化，调整也比较频繁。

因此，我逐渐把它优化成现在的文件夹形式，继续维护和使用。现阶段，我更希望先把方法打磨清楚，让它能在项目中用起来。

文件夹形式让我可以直接修改提示词、查看输入与产出、检查上下游承接，也让其他人更容易取用其中的部分内容。这是当前的使用选择，后续是否再做成完整软件，将根据实际需要决定。

## 3. 现在的章法包含什么

当前内容分为两部分。

**方法层**放在 `99-shared/prompts/`：包含 16 份分层提示词、节点清单、提示词编写规范，以及三个模拟示范项目。它回答“项目怎样推进、每一步怎样做”。

**使用者项目工作区**是根目录的 `00-code/` 至 `04-workspace/`：用于保存某个真实项目的输入、长期基线、需求台账、开发中产出和归档。目前这些位置保留为启动模板，文档随流程执行逐步生成。

README 和使用指南帮助人理解这套方法，`AGENTS.md` 和节点提示词为 AI 提供执行约定。项目事实由相应文档和台账保存。

当前提示词文档链已有模拟示范演练；代码开发、联通与真实发布仍需真实项目验证。示范材料的作用是展示结构和承接方式，其中的模拟验收和发布记录不能证明某个软件已经上线。

## 4. 怎样理解博客里的软件设想

[博客项目页](https://www.xiaozhifly.cn/projects/zhangfa/)记录了早期的软件设想，包括“规范包、状态引擎、进度界面”三层形态。理解当前文件夹版本时，可以这样对应：

| 早期设想 | 当前文件夹形式中的对应内容 |
|---|---|
| 规范包 | 分层提示词、编写规范、节点清单和 AI 工作约定 |
| 状态引擎 | 以提示词和台账规定状态操作，由人或 AI 执行并核对；尚未提供自动强制校验的软件引擎 |
| 进度界面 | 通过项目 README、需求池、版本注册表和发布日志查看进度；尚未提供完整软件界面 |

博客中描述的自动配齐材料、自动打回、开版本初始化、发布一键收口等能力，属于软件设想。当前使用时需要按照文件中的规则实际执行和检查。

当前使用方式以仓库说明和文件内容为准。博客保留项目背景，仓库承载可取用、可修改的方法资产。

## 5. 为什么把它开源出来

我希望分享的是一套自己持续维护和使用的方法。其他人可以拿来启动项目、参考文档结构，或者根据自己的工作方式调整提示词和目录约定。

也希望借助真实使用反馈，发现哪些规则有帮助、哪些文档过重、哪些承接容易出错。对我而言，开源的意义在于让方法被使用、被讨论，并在这些反馈中继续改进。

使用者可以保留完整工作流，也可以取用其中一部分；调整后，应同时理顺相关输入、产出和台账关系。模拟示范的业务内容不应直接变成自己项目的事实。

## 6. 接下来怎样维护

现阶段会继续围绕文件夹形式完善提示词、流程、示范和使用说明。对于反复出现的问题，优先找出规则或提示词中的原因，再验证修改能否改善后续产出。

软件形态的后续安排取决于真实使用需要，目前没有固定发布时间。仓库也不承诺适用于所有项目；欢迎通过[维护与贡献](./维护与贡献.md)中说明的方式交流实际问题。
