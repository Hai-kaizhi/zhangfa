# 章法使用指南

本指南说明怎样用文件夹形式的章法启动和推进项目。节点顺序、必选与按需划分、产出路径以[开发路径与节点清单](../99-shared/prompts/00-开发路径与节点清单.md)为准；具体执行要求以相应提示词为准。

## 1. 准备工作区

准备一个能读写 Markdown 的编辑器，以及你习惯使用的 AI 工具。章法的方法文件不依赖特定 AI 厂商；当前也没有需要启动的管理服务。

从[仓库](https://github.com/Hai-kaizhi/zhangfa)获取文件后，建议为每个真实项目保存一份独立副本。根目录 `00-code/` 至 `04-workspace/` 用来存放该项目的材料，`99-shared/prompts/` 保存方法文件，`references/` 保存模拟示范。

如果只想了解方法，先读[初衷与当前形态](./初衷与当前形态.md)和[项目总览](../项目总览.md)。如果要开始项目，继续下面的步骤。

## 2. 分清材料和提示词

| 内容 | 放在哪里 | 怎样使用 |
|---|---|---|
| 原始想法、需求、已确认决定 | `01-project-docs/00-inputs/01-原始需求.md` | 作为第一个节点的输入；当前模板未预置，开始项目时自行创建 |
| 节点提示词 | `99-shared/prompts/` 的对应层级目录 | 阅读任务、约束、格式和输入要求，再执行 |
| 项目级产出 | `01-project-docs/` 的相应节点目录 | 检查确认后，作为下游依据 |
| 业务命名 | `01-project-docs/术语表.md` | 首次定名时创建，后续节点沿用并维护 |
| 需求与版本记录 | `02-requirement-pool/` | 由入池、认领、发布节点在首次需要时创建和更新 |
| 开发中材料 | `04-workspace/v<X.Y.Z>/` | 认领时创建，保存本小版本的 PRD 与交付材料 |
| 版本归档 | `03-versions/major/<版本>-<名称>/v<X.Y.Z>/` | 发布时归档，供后续查阅和承接 |

不要预先批量创建空 PRD、空交付说明或空验收记录。先有输入，再按节点生成实际内容。

## 3. 从第一个节点开始

先把真实的项目想法写入原始需求文件。写清准备服务谁、遇到了什么问题、希望做到什么、有哪些已经确认的决定，以及哪些内容还没想清楚。零散材料也可以作为起点。

打开[概念文档提示词](../99-shared/prompts/01-project/01-提示词-概念文档（项目）.md)，按“输入”章提供材料。产出位置是：

```text
01-project-docs/01-concept/01-概念文档（项目）.md
```

如果 AI 可以访问工作区，可以用下面的话术起步：

```text
请先读 AGENTS.md 和 99-shared/prompts/00-开发路径与节点清单.md。
本次只执行 99-shared/prompts/01-project/01-提示词-概念文档（项目）.md。
原始输入是 01-project-docs/00-inputs/01-原始需求.md。
按该提示词执行，将结果写入其规定的产出路径。
生成只使用当前节点要求的输入，不读取评审材料或未指定的示范正文。
材料中的已确认决定、建议和未知事项请分别保留状态。
完成后检查结构、命名和输入承接，报告产出位置及需要确认的事项。
```

如果 AI 只能在聊天中接收文字，就把提示词和它要求的输入粘贴到同一对话，取得结果后手动保存。涉及台账修改、文件归档和清理的节点，也需要由你落实文件操作并核对。

检查概念文档是否准确表达了项目方向。会影响服务对象、主要流程或范围的疑问先处理，再继续项目 PRD。

## 4. 建立项目级基线

项目级顺序为 `01 → 02 → 03 → 04A / 04B / 04C → 05`，提示词入口见[提示词索引](../99-shared/prompts/README.md)。

| 节点 | 作用 | 选择要求 |
|---|---|---|
| 01 概念文档 | 收敛项目方向、参与者和主要能力 | 必选 |
| 02 PRD（项目） | 建立产品全景、核心闭环与关键规则 | 必选 |
| 03 技术文档 | 建立项目级技术方向 | 必选 |
| 04A 开发规范 | 约定真实实现的工程规则 | 真实代码交付前必选 |
| 04B UI（项目） | 形成 UI 生图脚本与风格锚定 | 按需 |
| 04C 模块设计 | 为复杂对象和跨模块协作补充设计 | 按需 |
| 05 产品路线图 | 明确大版本序列与各版范围 | 必选 |

`04A / 04B / 04C` 承接项目 PRD 和技术文档，可以并行；路线图在适用分支形成一致基线后收口。省略按需文档时，仍需在既定环节处理必要的设计工作。

术语表贯穿这些节点，随业务名称的确定同步维护。它没有独立提示词，也不是路线图完成后才补写的步骤。

## 5. 规划大版本，再把需求入池

从路线图中选择要推进的大版本，依次执行：

1. [01 PRD（大版本）](../99-shared/prompts/03-versions/major/01-提示词-PRD（大版本）.md)：确定本阶段功能和边界。
2. [02 开发顺序与需求拆解](../99-shared/prompts/03-versions/major/02-提示词-开发顺序与需求拆解（大版本）.md)：形成开发顺序、批次与功能级需求条目。
3. [需求池运营](../99-shared/prompts/02-requirement-pool/01-提示词-需求池运营（需求池）.md)：将条目按批量入池模式导入；来自沟通的独立新需求走单条入池模式。

大版本文件保存在 `03-versions/major/<版本>-<名称>/`。需求池提示词只负责入池；认领在下一步执行，发布在验收后执行。

需求池只保留活跃需求总表，状态为待规划／已认领／搁置。入池流水与后续历史记录写入发布日志，已发布需求从活跃池移出。

## 6. 认领一个小版本

执行[01 PRD（小版本）](../99-shared/prompts/03-versions/minor/01-提示词-PRD（小版本）.md)，提供提示词输入章要求的需求池、所属大版本两份文档、术语表和目标版本号。

这个节点包含前置检查、认领和 PRD 生成。材料不齐或没有待认领条目时，先补上游。通过检查后，节点圈定范围、更新池状态、追加认领流水、创建工作区 README、登记版本注册表，再生成开发级 PRD。

认领完成后核对三处：

- 需求池中本版条目为 `已认领（vX.Y.Z）`。
- `04-workspace/v<X.Y.Z>/` 中存在本版 README 和 PRD。
- 版本注册表中存在本版“开发中”记录，认领条目数一致。

PRD 的需求名、用途和验收标准沿用上游验收锚。后续修订已认领版本的 PRD，按提示词的修订分支处理，避免重复认领。

## 7. 选择开发路线，执行验收

本版有界面设计需要时执行[02 UI（小版本）](../99-shared/prompts/03-versions/minor/02-提示词-UI（小版本）.md)。它沿用项目层风格锚定，只覆盖本版认领范围。

开发路线二选一：

| 路线 | 适用的推进方式 | 执行顺序 |
|---|---|---|
| 03A 全阶段 AI 开发 | 一次完成前端、后端与数据实现 | [03A](../99-shared/prompts/03-versions/minor/03A-提示词-全阶段AI开发（小版本）.md) |
| 03B 前端与 Mock，再联合数据与能力 | 先确认前端闭环，再替换 Mock、联通真实后端和数据库 | [03B1](../99-shared/prompts/03-versions/minor/03B1-提示词-前端与Mock（小版本）.md) → [03B2](../99-shared/prompts/03-versions/minor/03B2-提示词-数据与能力联合（小版本）.md) |

完成开发后，按本版 PRD 的验收锚逐条执行黑盒验收，将真实结论与证据写入交付说明。04 验收没有独立提示词，也不要求额外生成一份测试文档。

验收不通过时修正问题并再次验收，通过且有证据后再执行发布。AI 写出的“通过”需要与实际操作结果对应。

如果只是练习文档流程，可以使用明确标注的模拟输入和模拟证据；应保留“文档范本演练、模拟证据”性质，与真实开发和发布结果区分。

## 8. 发布与归档

[05 发布与归档](../99-shared/prompts/03-versions/minor/05-提示词-发布与归档（小版本）.md)是小版本的唯一发布出口。验收通过且池状态就绪后，按提示词执行五个动作：

1. 将本版工作区产出归档至所属大版本目录下的 `v<X.Y.Z>/`，补归档说明。
2. 将本版需求从活跃需求池移出。
3. 将版本注册表中的本版更新为已发布。
4. 追加发布日志三节：发布记录／需求归档明细／池变更记录。
5. 清理本版开发中产出，工作区 README 留下归档指路。

完成后逐项核对。归档位置、发布时点和条目数在归档说明、版本注册表、发布日志中应一致；操作只影响本版。

这里的发布是项目文件与台账中的发布流程。网站部署、应用安装包、Git tag 和 GitHub Releases 按实际项目选择，需要另有真实执行结果。

## 9. 每一步怎样检查

执行者默认可以直接生成单文档或常规节点产出，是否需要子智能体按 [AGENTS.md](../AGENTS.md) 的执行方式分级判断。由主智能体亲自审核，涉及项目方向的决定由使用者确认。

检查时至少关注：

- 章节结构和数量是否符合当前节点要求，编号是否连续。
- 需求名、用途、验收锚是否与上游逐字一致，业务命名是否沿用术语表。
- 是否残留其他项目名称，是否把推断或模拟结果写成事实。
- 产出路径、台账状态、条目数和归档关系是否一致。
- 含 Mermaid 图时，是否用 Chrome 与 `mermaid@10` 实际渲染，核对 SVG 数量并检查 `Syntax error`。

生成输入只取当前节点“输入”章指定的文件，评审材料不作为生成输入；示范正文仅在使用者明确指定对应单篇时取用。

单次遗漏或排版问题可以就地修正文档。多次出现的结构、承接或规则缺陷，应先修提示词，再用限定输入重新生成受影响产出并检查，操作方式见[维护与贡献](./维护与贡献.md)。

## 10. 已有项目与日常继续工作

已有项目可以先整理现有材料，按节点要求核对哪些输入已经具备、哪些基线仍需补齐。保留已确认决定和真实历史，按依赖进入下一个节点；不必为了套模板重写已经准确的内容。

隔一段时间继续项目时，先查需求池、版本注册表和工作区 README：确认当前认领范围、活动版本、已有产出和下一步。对照节点提示词补齐本次输入，再继续执行。

章法的方法文件还会调整。更新自己的副本时，先比较提示词与规则的变化，再合并适用修改，并检查是否影响现有产出；已有项目的事实与历史台账继续保留。
